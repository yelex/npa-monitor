# План реализации (сгенерирован Claude, 2026-08-19)

## 1. Архитектура

Три независимых процесса + общая БД:
- **parser/** — cron/systemd timer, ежедневный batch-job: `sources/` (адаптеры под источники), `fetcher.py` (httpx+tenacity, retry), `classifier.py` (ключевые слова → категория/приоритет), `dedup.py`, `state.py` (доверстывание пропусков).
- **bot/** — aiogram 3 (async, встроенный FSM для многошаговых сценариев: запрос ссылки на НПА, причины отклонения), long-running polling-процесс, не вебхук.
- **db/** — SQLAlchemy 2.0 + Alembic, общий слой для parser и bot.

Parser и bot — разные процессы (не один монолит), чтобы падение одного не роняло другой; связывает их только БД. PDF: PyMuPDF/pdfplumber + pytesseract как fallback. Docker Compose на VPS.

## 2. БД: SQLite для MVP

Один эксперт, обход раз в сутки, десятки сигналов/день — SQLite в WAL-режиме достаточен, бэкап = `cp` файла, нет отдельного сервиса БД на VPS. Переход на Postgres через SQLAlchemy почти бесшовен (расширение на 89 регионов, несколько экспертов, полнотекстовый поиск).

Таблицы:
- `signals` — карточка сигнала (поля из раздела 7 AGENTS.md)
- `signal_categories` — M2M (сигнал → несколько ЖС)
- `status_history` — аудит переходов (нужно для напоминаний >3 дней)
- `sources_state` — per-source дата последнего успешного обхода (доверстывание)
- `documents_seen` — дедуп независимо от создания сигнала
- `experts` — whitelist

## 3. Переиспользование `measure_deepagent`

Ревью репозитория — первая задача Этапа 0, до написания `parser/sources/`. Потенциально полезно: fetcher/HTML+PDF-парсер источников (если есть рабочие адаптеры) и JSON-схема карточки меры. Экстрактор карточек — внешний контур («агент автообновления»), сюда не входит.

## 4. Этапы (человеко-дней, один разработчик)

| # | Этап | Оценка |
|---|---|---|
| 0 | Подготовка (ревью measure_deepagent, список источников Москвы, проверка PDF) | 1–2 дн |
| 1 | БД и общий слой | 1–2 дн |
| 2 | Parser MVP | 4–6 дн |
| 3 | Bot MVP | 3–4 дн |
| 4 | Интеграция / сквозной сценарий | 2 дн |
| 5 | Деплой | 1–2 дн |
| 6 | Пилот с экспертом (наблюдение, не разработка) | 1–2 нед |

Итого разработка: **~12–18 человеко-дней**.

## 5. Ответы на открытые вопросы (раздел 12 AGENTS.md)

1. Схема БД — см. п.2.
2. PDF/OCR — fallback-архитектура сразу: текстовый слой основной, OCR (tesseract ru) только если текст пустой/короткий; уточнить на реальных примерах на Этапе 0.
3. Источники Москвы — ручная фиксация на Этапе 0 (mos.ru, минтруд/соцзащита Москвы, портал правовой информации), блокер для Этапа 2.
4. Дата вступления в силу — regex-эвристики на первой итерации («вступает в силу с…»), LLM-разбор вторым проходом, если покрытие низкое по итогам пилота.
5. Повторное открытие «Отклонён» — команда `/reopen <id>`, перевод в «Новый» с записью в `status_history`; не противоречит требованиям (там про автоматический невозврат, не запрет ручного).
6. Связь с `measure_deepagent` — не жёсткая зависимость, опциональное переиспользование fetcher/parser-кода как библиотеки после ревью на Этапе 0.
