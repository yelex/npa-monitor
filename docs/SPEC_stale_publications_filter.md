# Спека: публикации многолетней давности проходят как «новые» сигналы

Статус: **реализовано частично, 2026-08-24** — см. раздел 5 (результат) и раздел 4
(что осознанно не сделано в этой итерации и почему). Источник задачи — PLAN.md, Фаза 9,
п.1 (обратная связь аналитика по живому дампу 105 сигналов, `signals_dump.txt`, прогоны
2026-08-20…24; сам файл не входит в этот репозиторий — снят на VPS, здесь недоступен).

## 1. Проблема

Аналитик обнаружил в живой сводке сигналы по публикациям многолетней давности
(2003–2023), которые прошли как «новые»: `kremlin.ru` листинг 2003/2008 г., `mos.ru`
новости 2022 г., `sfr.gov.ru` интервью 2023 г. (см. AGENTS.md раздел 16 п.15,
PLAN.md Фаза 9 п.1). Причина в общем виде — `parser/state.py`/`parser/orchestrator.py`
проверяют только «URL не видели за окно обхода» (`documents_seen`), а не фактическую
дату контента; у части источников URL создаёт иллюзию свежести.

## 2. Ограничения расследования в этой сессии

Нет доступа к `signals_dump.txt` (снят на VPS, не закоммичен) и нет живого сетевого
доступа к RSNET-доменам (`kremlin.ru` требует `RU_PROXY_URL`, недоступен из этой среды
без подтверждённого allow-листа на момент сессии, AGENTS.md раздел 16 п.7). Поэтому
конкретные URL из четырёх под-пунктов чек-листа (PLAN.md Фаза 9 п.1) не воспроизведены
вживую в этой итерации — ниже описаны причины по коду (раздел 3) и то, что можно
исправить/протестировать синтетически без живого прогона (раздел 5), отдельно от того,
что требует либо живой проверки, либо архитектурного расширения (раздел 4).

## 3. Разбор по коду

**`parser/orchestrator.py::process_source`** останавливает пагинацию источника, как
только встречает публикацию старше `window_start` — но только если
`pub.published_at is not None`:

```python
if pub.published_at is not None and pub.published_at < window_start:
    reached_window_start = True
    break
_process_publication(session, classifier, pub, whitelisted_domains, result)
```

Если адаптер не смог извлечь дату (`published_at is None` — например, `<time>`-элемент
отсутствует в разметке конкретной записи листинга), эта публикация **не только не
останавливает обход, но и обрабатывается как обычная** — ни разу не проверяется на
«старше окна». На глубокой странице пагинации (`kremlin.ru/acts/news/page/N`,
`MAX_PAGES_PER_SOURCE = 5`) это означает: если разметка старых/архивных страниц не
даёт машиночитаемую дату (правдоподобно для `kremlin.ru` — упомянутый в обратной связи
URL `catalog/keywords/.../events/page/N` не совпадает с URL-шаблоном текущего адаптера
`parser/sources/kremlin.py`, значит либо разметка изменилась, либо это URL самой
публикации, найденный `itemprop="url"`-ссылкой внутри листинга, а не URL страницы
листинга) — обход продолжает создавать сигналы без всякой защиты по дате. Это общий
архитектурный пробел, не специфичный для kremlin.ru: **любой источник, отдающий
публикацию без даты, полностью обходит проверку окна**.

`sfr.gov.ru`: текущий адаптер (`parser/sources/sfr.py`) обходит только
`press_center/news/` — URL-шаблон результата `press_center/news/~YYYY/MM/DD/ID`
(проверено тестом на реальной вёрстке, `tests/test_sources_sfr.py`). Путь
`/branches/<region>/info/~<дата>/<id>?info_category=N`, упомянутый в обратной связи
(AGENTS.md раздел 16 п.15, PLAN.md Фаза 9 п.1) — не URL самого листинга, который
обходит адаптер, а, судя по всему, URL конкретных статей, на которые ссылается
национальный листинг `press_center/news/` (перепубликация одного и того же
статичного/справочного материала по отделениям, с рансующейся датой в пути,
не отражающей фактическую дату контента). Название пути (`info`, не `news`) —
единственный доступный сейчас программный признак таких публикаций.

## 4. Что не сделано в этой итерации (осознанно, с обоснованием)

- 🔴 **Извлечение даты публикации из содержимого целевой страницы** (не только из
  листинга) — п.1 чек-листа PLAN.md Фаза 9. Это архитектурное расширение: сейчас
  парсер скачивает полный текст документа только для ссылки на НПА, которую прислал
  эксперт (`bot/main.py::on_npa_link`), а не для каждой найденной в листинге
  публикации — добавление такого скачивания на каждую публикацию при обходе (десятки
  публикаций/источник/день) увеличивает число сетевых запросов на порядок и требует
  решения, что считать «содержимым» для HTML-страниц разной вёрстки на 12 источниках.
  Не начато — нужно отдельное архитектурное решение (возможно, только для источников
  с уже обнаруженной проблемой рансующихся дат, не для всех), не вписывается в разовый
  фикс-коммит.
- 🔴 Конкретная причина расхождения `kremlin.ru/catalog/keywords/.../events/page/N` (раздел
  3) — не подтверждена вживую (нет доступа к RSNET в этой сессии). Реализованная в
  разделе 5 защита (стоп пагинации при полностью недатированной странице) закрывает
  этот класс риска в общем виде, но не эту конкретную гипотезу.

## 5. Реализовано в этой итерации

**5.1. Пагинация останавливается, если страница листинга полностью без дат.**

`parser/orchestrator.py::process_source` — если ни одна публикация на странице не
содержит `published_at` (весь `page` — `None`), считаем, что источник не даёт
достаточно информации для проверки окна на этой глубине пагинации, и не идём дальше
(текущая страница всё равно обрабатывается — публикации без даты по-прежнему могут
быть релевантны, отбрасывать их целиком не в мандате этой задачи, раздел 4). Это не
специфично для kremlin.ru — общий защитный механизм: не позволяет ни одному источнику
бесконтрольно углубляться в пагинацию, если не может подтвердить, что материалы
попадают в окно (PLAN.md Фаза 9 п.1, 4-й под-пункт: «на кумулятивных индексах остановка
… должна применяться и здесь»).

**5.2. Исключение `sfr.gov.ru/branches/*/info/` из источников сигналов.**

`parser/filters.py::is_excluded_path(url)` — новая функция, URL-паттерн-фильтр (список
`_EXCLUDED_PATH_PATTERNS`, легко расширяемый) для статичных/справочных страниц, которые
не являются публикациями о событии (раздел 3). Подключена в
`orchestrator.py::_process_publication` перед дедупом — совпадение считается не
дубликатом и не нерелевантной публикацией, а отдельной категорией (`SourceRunResult.excluded`),
чтобы в логах/статистике обхода было видно, что публикация осознанно отфильтрована
паттерном пути, а не провалила классификацию.

**5.3. Регрессионный тест на доверстывание пропуска выходных (понедельник).**

PLAN.md Фаза 9 п.1, 2-й под-пункт, требовал «проверить, что `fetch_window_start` уже
даёт это» — код уже был правильным (раздел `parser/state.py`, докстринг: «с даты
последнего успешного обхода, сколько бы дней назад он ни был»), не хватало теста на
конкретно этот сценарий. Добавлен `tests/test_state.py::
test_fetch_window_start_covers_skipped_weekend_when_run_monday_after_friday` — источник
последний раз успешно обошли в пятницу, `fetch_window_start` в понедельник с этим
источником возвращает пятницу (не воскресенье/полночь понедельника).

## 6. Открытые вопросы

1. 🔴 Извлечение даты из содержимого целевой страницы (раздел 4) — нужно решение по
   архитектуре (для всех источников или только для источников с подтверждённой
   проблемой рансующихся дат) и оценка сетевой нагрузки, прежде чем начинать.
2. 🟡 Подтвердить на боевом VPS (с рабочим `RU_PROXY_URL`), действительно ли
   `kremlin.ru` отдаёт страницы без дат на глубокой пагинации — раздел 5.1 закрывает
   риск защитно, но не подтверждает диагноз раздела 3 буквально.
3. 🟡 Список `_EXCLUDED_PATH_PATTERNS` (`parser/filters.py`) сейчас содержит только
   `sfr.gov.ru/branches/*/info/` — расширять по мере обнаружения новых паттернов
   (аналогично `_EXACT_WORD_OVERRIDES` в `parser/ru_stem.py`, AGENTS.md раздел 16 п.13).
