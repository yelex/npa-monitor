# Спека: калибровка Stage B v2 — план эксперимента по альтернативам (после вердикта 03.09)

## Статус
- [ ] Черновик — план эксперимента. **Реализация не начата** (эта спека фиксирует
  подход и порядок экспериментов, не код).

## Контекст

Stage B (`parser/hybrid_classifier.py`, docs/SPEC_hybrid_classifier.md) — гибридный
fallback-классификатор ЖС (BM25 + rubert-tiny2 cosine, RRF k=60), задеплоен 02.09.
Калибровка 03.09 на честных выборках (`scripts/collect_heldout.py`, 60 дней
pravo.gov.ru, ~23k документов → `data/heldout_samples.json`: 25 held-out «потерянных
Stage A» + 17 твёрдых негативов + 1 uncertain-кейс Марий Эл) дала **вердикт: гибрид
не проходит приёмку** — ни в одной точке порогов не достигаются одновременно
recall ≥ 0.60 (выборка 2) и specificity ≥ 0.85 (выборка 3):
- Попытка 1 (стоп-слова BM25 из topic_block): specificity 0.76→0.88 ✅, recall
  0.64→0.36 ❌.
- Попытка 2 (раздельные якоря: полные для косинуса, отличительные для BM25,
  `data/hybrid_anchors.yaml` + `db/catalog.py::HybridAnchor.bm25_anchor`): grid search
  — recall 0.24–0.28 при specificity 0.88–0.94, recall перестал зависеть от t_bm25.

Диагноз: rubert-tiny2 cosine на коротких канцелярских заголовках НПА не дотягивается
до порога различимости категорий; BM25 подтверждает истинные срабатывания на тех же
общих словах, что дают ложные («меры социальной поддержки <чужая ЖС>»). Это предел
именно этого признакового пространства (rubert-tiny2 + BM25 на текущих якорях), не
порогов — подробности `docs/SPEC_hybrid_classifier.md` раздел «Калибровка 03.09»,
`PLAN.md` раздел «Статус калибровки Stage B (03.09)».

**Текущее состояние в проде:** Stage B на стартовых порогах — specificity 1.00,
recall ~0 (фактически не срабатывает, но и не портит точность). Ничего не блокирует
прод: Stage A + хотфикс словаря (`life_situations.yaml::svo`) закрывают мотивирующий
кейс 412-П. Эта спека — не срочный фикс, а план следующей итерации из бэклога
(`PLAN.md` п.1).

Три альтернативы зафиксированы (в порядке приоритета, `PLAN.md`/`AGENTS.md` разд.16):
1. Qwen3-Embedding-0.6B ONNX вместо rubert-tiny2.
2. LLM-ассист на границе confidence (near-miss → GigaChat/GLM).
3. Якоря-пары «заголовок→категория» из размеченной БД (236+ сигналов).

## Проблема

Нужно решить, куда двигаться дальше, вместо повторного тюнинга порогов на той же
модели (уже пройдено две итерации, обе упёрлись в потолок признакового
пространства). Требуется: (а) порядок экспериментов с ожидаемой отдачей и
стоимостью, (б) конкретные критерии приёмки на тех же честных выборках, (в) бюджет
итераций и стоп-правило, чтобы не залипнуть на четвёртой попытке тюнинга того же
самого.

## Предполагаемый план (порядок экспериментов)

Порядок — по ожидаемой отдаче относительно инженерной стоимости и риска, не по
номеру в бэклоге механически: Qwen3 — наименее рискованная замена (тот же харнесс
RRF/BM25/пороги, меняется только эмбеддер), LLM-ассист — уже есть готовая
инфраструктура (`parser/llm.py::get_default_client()`, GLM), якоря-пары — методологически
самый рискованный (см. риски ниже), поэтому последний.

### Эксперимент 1 — Qwen3-Embedding-0.6B вместо rubert-tiny2

Артефакты: `/root/dev/auto/agent/src/src/product_agent/extraction_service/models/qwen3-embedding-0.6b/`
(`model.onnx` 613 МБ, `model_quantized.onnx` 613 МБ — **квантизация для этой модели
почти не уменьшает размер**, в отличие от rubert-tiny2, где `model_quantized.onnx`
29 МБ против `model.onnx` 116 МБ; это первое, что нужно проверить, а не считать
данностью «раз ONNX — значит лёгкий»).

Отличия подключения от `RubertTinyEmbedder` (эталон — `auto/agent/src/src/
core/embeddings.py::LocalOnnxBackend._encode`, не `semantic_retriever.py`, который сам
rubert-tiny2):
- **Last-token pooling**, не mean-pooling (`use_last_token = "qwen" in path`).
- ONNX-граф с KV-cache: нужны `position_ids` (arange по длине последовательности) и
  пустые `past_key_values.*` (`np.zeros((batch, 8, 0, 128))`) — модель без них не
  запустится теми же входами, что rubert-tiny2.
- Instruct-префикс для запроса (не для документов/якорей) — `"Instruct: Найти самую
  релевантную запись к запросу пользователя...\nЗапрос: {text}"` — asymmetric
  encoding, отличается от симметричного cosine у rubert-tiny2.
- Микро-батчинг (`EMBEDDING_MICRO_BATCH_SIZE=16`, `EMBEDDING_MAX_SEQ_LENGTH=512` в
  `auto/core/config.py`) — используется в `auto` специально для предотвращения OOM
  при инференсе этой модели, не только при загрузке весов. Раз в проекте с бóльшим
  железом уже потребовался этот костыль, на 12 ГБ VPS npa-monitor его тоже нужно
  закладывать сразу, не как реакцию на инцидент.

**Шаги:**
1. RAM-проверка ДО переноса кода: поднять `model_quantized.onnx` локально (host, не
   в контейнере бота), загрузить сессию + токенизатор, прогнать батч из ~30 якорей +
   1 заголовок, замерить пиковый RSS процесса (`resource.getrusage` или `/proc/self/status`
   VmHWM). Сравнить с текущим потреблением rubert-tiny2 в контейнере парсера/бота
   (baseline). Порог отказа: если пиковый RSS этого одного процесса приближается к
   заметной доле свободной памяти сервера (сейчас `free -h`: ~11 ГБ всего, ~8 ГБ
   available, но это делится с ботом/парсером/прокси в Docker-compose, не резерв
   только под Stage B) — не продолжать эксперимент, сразу переходить к
   эксперименту 2.
2. Если RAM ок — `Qwen3Embedder` класс по образцу `RubertTinyEmbedder`
   (`parser/hybrid_classifier.py`), с учётом четырёх отличий выше. Артефакты в
   `parser/models/qwen3-embedding-0.6b/` (COPY в Dockerfile — 613 МБ увеличивает
   образ заметно больше, чем rubert-tiny2's 29 МБ; проверить, укладывается ли в
   `<50 МБ в git` правило из SPEC_hybrid_classifier.md или нужен download-скрипт
   вместо коммита весов).
3. Пересчитать якоря (`data/hybrid_anchors.yaml`) через новый эмбеддер, прогнать
   `scripts/calibrate_hybrid.py --samples data/heldout_samples.json` с чистым grid
   search по `T_cos` — **не переносить 0.60 как стартовую точку**, instruct-тюненные
   эмбеддинги живут на другой шкале похожести, чем rubert-tiny2 (сканировать заново,
   например 0.30–0.85 с шагом 0.05). `T_bm25`/BM25-слой не меняется (модель-независим).

### Эксперимент 2 — LLM-ассист на границе confidence

Когда Stage B даёт near-miss (лидер по RRF есть, зазор проходит, но ни `cos_top1`,
ни `bm25_top1` не дотянули до порога) — вместо молчаливого отказа спросить GLM
(`parser/llm.py::get_default_client()`, уже интегрирован, паттерн — опциональный
второй проход, AGENTS.md разд.5) один закрытый вопрос: «эта публикация о ЖС X:
да/нет» с заголовком (+ якорем-кандидатом для контекста).

**Шаги:**
1. Оценить объём near-miss ДО прототипа: прогнать `calibrate_hybrid.py` на боевых
   логах/trace (`ClassificationTrace`, near-miss пишется туда с 02.09 по п.7 спеки
   гибрида) или на `data/heldout_samples.json`, посчитать долю near-miss от общего
   числа документов, доходящих до Stage B (не от всех ~23k/60 дней — Stage B
   запускается только когда topic_block/document_marker уже совпали и Stage A
   ЖС не нашёл — это подмножество, реальный размер нужно взять из трейс-лога прод,
   не предполагать). Это определяет и латентность, и стоимость.
2. Прогнать те же 25+17+1 через LLM-гейт отдельно (без остального RRF-пайплайна) —
   recall/specificity именно LLM-ответа на этой выборке.
3. Замерить латентность одного вызова (важно для боевого крон 06:00 → сводка
   ~08:00, AGENTS.md разд.14) и прикинуть стоимость по объёму из шага 1.
4. Скомбинировать: near-miss → LLM → итоговое решение; прогнать
   `calibrate_hybrid.py`-эквивалент с LLM-гейтом на honest-выборках.

### Эксперимент 3 — якоря-пары «заголовок→категория» из БД (236+ сигналов)

Использовать заголовки уже размеченных исторических сигналов (подтверждённая
эксперетом категория) как дополнительные якоря — расширение косинус-индекса и/или
BM25-корпуса сверх 7–8 якорей на ЖС.

**Риск методологии (см. «Риски» ниже) — если запускать, то последним и с явным
контролем утечки:** исторические сигналы — это по построению то, что Stage A/старый
пайплайн УЖЕ поймал; они систематически не похожи на кейс, который Stage B должен
закрывать (то, что Stage A пропускает). Использовать как ground truth для порога
принятия — методологическая ошибка; годится разве что для расширения
BM25-стоп-слов/covered-vocabulary, не как источник новых «хороших» якорей без
дополнительной курации вручную.

## Критерии приёмки

Без изменений от исходной спеки (`docs/SPEC_hybrid_classifier.md`), но обе цели —
**одновременно**, в одной точке порогов, не по отдельности:
- Выборка 2 (held-out, `data/heldout_samples.json::sample_2_held_out`, n=25):
  recall ≥ 0.60.
- Выборка 3 (контроль, `sample_3_control`, n=17, `sample_3_uncertain` — вне метрики):
  specificity ≥ 0.85.
- Выборка 1 (не-регрессия, ~146 исторических сигналов из БД,
  `calibrate_hybrid.py --db ...`): precision ≥ 0.90 — прогонять заново при любой
  смене модели/порогов, не только выборки 2/3.

Дополнительно для этой итерации:
- Любая точка, прошедшая критерии на n=25/17, повторно проверяется на **свежей**
  выборке (другое окно `scripts/collect_heldout.py --days N`, не то же самое
  60-дневное окно, использованное для подбора порогов) — n=25/17 достаточно мало,
  чтобы grid search мог случайно попасть в точку, работающую только на этих
  конкретных примерах (тот же класс риска, что и попытка 1: stop-слова хорошо
  выглядели на бумаге, обвалили recall).

## Метод калибровки

- `scripts/calibrate_hybrid.py --samples data/heldout_samples.json` — без изменений
  интерфейса для замены эмбеддера (модель подключается через тот же `_StageBContext`,
  меняется только класс эмбеддера и, при необходимости, диапазон grid search по
  `T_cos`).
- Grid search — тот же паттерн, что попытка 2 03.09 (`/tmp/grid2.out`): перебор
  `T_cos × T_bm25 × RRF-зазор`, вывод в `/tmp/grid_v2_<эксперимент>.out` для
  воспроизводимости хода эксперимента (не коммитить, как и раньше).
- Leave-one-out на выборке 2+3, как в исходной спеке — с оговоркой про малый n
  (см. «Критерии приёмки» выше, доп. проверка на свежей выборке).
- Для эксперимента 3 (якоря из БД): исключить из кандидатов в якоря все заголовки,
  уже присутствующие в `data/heldout_samples.json` — иначе утечка eval-выборки в
  обучающие данные (якорь = дословный заголовок held-out примера даёт
  cos-совпадение ≈1.0 не за счёт качества модели).

## Бюджет итераций

- Эксперимент 1 (Qwen3): до 1 дня — RAM-проверка (часть дня, стоп-условие описано
  выше) + перенос эмбеддера + grid search. Если RAM-проверка проваливается —
  прекратить в тот же день, перейти к эксперименту 2.
- Эксперимент 2 (LLM-ассист): 1–2 дня — оценка объёма near-miss из прод-трейса
  (быстро) + прогон LLM-гейта на honest-выборках + оценка латентности/стоимости.
- Эксперимент 3 (якоря из БД): 0.5–1 день, только если 1 и 2 оба не прошли приёмку.
- **Стоп-правило:** как только любой эксперимент по отдельности проходит оба
  критерия (recall ≥0.60 И specificity ≥0.85) на честных выборках — остановиться,
  не прогонять оставшиеся «для полноты». Это уже принятый в проекте принцип
  экономности (GLM как опциональный второй проход, не дефолт, AGENTS.md разд.5).
- Общий потолок — около недели инженерного времени. Если ни один из трёх
  экспериментов не проходит приёмку — не открывать четвёртую попытку тюнинга без
  паузы: вернуться к пользователю с продуктовым вопросом (жить с Stage B
  «выключенным по приёмке» постоянно, как сейчас — это допустимый исход, раздел
  «Статус калибровки Stage B (03.09)» в `PLAN.md` уже фиксирует, что прод ничем не
  заблокирован — или инвестировать в подход вне этих трёх, например LLM-классификация
  каждого документа вместо гейта только на границе).

## Риски

- **RAM.** Сервер — 12 ГБ (см. `free -h`: ~11 ГБ всего, делится с ботом, парсером,
  БД, прокси в Docker-compose, не резерв только под Stage B). Веса Qwen3 — 613 МБ
  что для файла, что для «quantized»-варианта (в отличие от rubert-tiny2, где
  quantized реально в 4 раза меньше) — не считать квантизацию автоматической
  экономией памяти для этой модели, измерять напрямую. В `auto` (более крупное
  железо) микро-батчинг понадобился даже там, чтобы не поймать OOM на инференсе,
  не только на загрузке весов, — значит на 12 ГБ VPS это не опциональная
  оптимизация, а обязательное условие для эксперимента 1.
- **Латентность / окно доверстывания.** Боевой крон — 06:00, сводка ~08:00
  (AGENTS.md разд.14). Обычный дневной прогон — небольшое окно, но доверстывание
  после сбоя (раздел 4 AGENTS.md) может уйти на 60 дней, как при сборе held-out
  (~23k документов). Qwen3-инференс на документ тяжелее rubert-tiny2 даже
  батчами; LLM-гейт добавляет сетевой round-trip на каждый near-miss. Нужно
  прикинуть худший случай (объём кандидатов Stage B за 60 дней, не всех 23k —
  см. «Метод калибровки», брать из прод-трейса) и проверить, что он укладывается
  до 08:00, а не предполагать.
- **Стоимость LLM.** GLM-вызовы дешёвые при низком объёме (гейт только на
  near-miss), но конкретная цифра ₽/месяц не оценена — считать после шага 1
  эксперимента 2 (замер объёма near-miss), не раньше.
- **Переобучение под маленькую выборку.** n=25 (held-out) / n=17 (контроль) —
  grid search, прошедший критерии, обязательно проверять на свежем независимом
  срезе (см. «Критерии приёмки»), не считать leave-one-out на тех же 42 примерах
  достаточным сам по себе — прецедент (попытка 1 03.09) уже показал, как легко
  локально выглядящий фикс на этих данных ломает recall.
- **Смещение якорей-пар из БД (эксперимент 3).** Исторические сигналы
  систематически не представляют случай, который Stage B должен закрывать
  («Stage A это пропустил») — см. «Эксперимент 3» выше. Не использовать без
  явной курации и контроля утечки eval-выборки.
- **Регрессия на выборке 1.** Любая смена модели/порогов может изменить итоговую
  точность и на публикациях, которые Stage A и так находит правильно (если Stage B
  когда-либо переопределяет решение Stage A — проверить в коде интеграции
  `parser/classifier.py::Classifier.explain`, что это по-прежнему только
  fallback, не переопределение) — перепрогонять `--db` на каждой итерации, не
  только выборки 2/3.

## Как воспроизвести / запустить эксперимент

```
# Базовый прогон на честных выборках (текущая rubert-tiny2 модель, baseline):
.venv/bin/python scripts/calibrate_hybrid.py --samples data/heldout_samples.json \
    --db <путь к БД с историческими сигналами>

# Grid search по порогам (пример, адаптировать диапазон под эксперимент):
for t_cos in 0.30 0.40 0.50 0.60 0.70; do
  for t_bm25 in 2.0 4.0 6.0; do
    .venv/bin/python scripts/calibrate_hybrid.py --samples data/heldout_samples.json \
        --t-cos "$t_cos" --t-bm25 "$t_bm25"
  done
done | tee /tmp/grid_v2_<эксперимент>.out

# Свежая held-out выборка для контроля переобучения (другое окно, не коммитить
# в data/ до ручной курации):
RU_PROXY_URL=http://95.142.42.28:8888 .venv/bin/python scripts/collect_heldout.py \
    --days 60 --out /tmp/heldout_candidates_v2.json
```

## Вне scope

- Замена/переписывание Stage A (`parser/classifier.py::match_categories`) — не
  трогается, как и в исходной спеке.
- Реализация выбранной альтернативы в проде — эта спека только план эксперимента и
  калибровки; если альтернатива проходит приёмку, перенос в прод — отдельная
  спека/PR с собственным ревью.
- BM25-solo режим — уже решено не гонять (`docs/SPEC_hybrid_classifier.md`, «Вне
  scope»), не пересматривается здесь.
- Расширение на регионы за пределами MVP (Москва + РФ) — не относится к этой
  итерации.
