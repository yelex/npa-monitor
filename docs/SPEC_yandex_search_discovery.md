Статус: **реализовано 2026-08-20**, в двух частях:
1. `parser/discovery_search.py::run_discovery_search`
   (`python -m parser.discovery_search`) — ручной CLI с явным периодом, для
   ретроспективного поиска/бэктеста (раздел 5, решение принято пользователем в пользу
   отдельного инструмента, не встраивания в `orchestrator.py`). Проверено вживую
   (раздел 4а) и живым прогоном без `--dry-run` — нашёл и создал сигнал именно для

2. `parser/discovery_search.py::run_daily_discovery`, вызывается из

Тесты — `tests/test_discovery_search.py` (21 тест: HTTP замокан, БД/классификатор

## 1. Проблема

Текущий `parser/orchestrator.py` находит публикации только через листинги источников
(`parser/sources/*`): обход постранично, окно поиска — 24 часа при обычном прогоне, 7
дней при первом запуске источника, с защитным лимитом `MAX_PAGES_PER_SOURCE = 5`
страниц за прогон (см. `parser/orchestrator.py`).

Это осознанно подходит для *ежедневного инкрементального* мониторинга (раздел 5
AGENTS.md), но не годится для:
- **ретроспективного поиска** («что изменилось за последние N месяцев» — например,
  для бэктеста/оценки качества классификатора на уже известных изменениях);
- **прицельного поиска конкретного НПА**, если известны только реквизиты/тема, а не
  источник и не точная дата (аналог того, что делает `search_and_fetch_npa` в
  `measure_deepagent`, см. `docs/STAGE0.md` раздел 1 — там сознательно не взяли, т.к.
  для ежедневного обхода это не требовалось);
- источников без глубокой постраничной истории на весь MVP-период (например,
  `mos.ru/authority/documents/` — 58 516 документов в реестре на 2026-08-20, по 10 на
  страницу; чтобы долистать до декабря 2025 года понадобились бы сотни запросов
  постранично — непрактично и не то, для чего сделан ежедневный обход).

## 2. Как это всплыло

Пользователь спросил, нашёл бы парсер изменения, задокументированные в
`docs/Для проверки обновления.xlsx` (сравнение 2025 vs 2026 по одному и тому же
`measureId`), если смотреть на полгода назад. Разобрал на конкретном примере:

- Мера `77_1`/`77_6` (компенсация за уход за ребёнком-инвалидом, Москва) выросла с
  16 783 ₽ / 38 459 ₽ до 17 790 ₽ / 40 767 ₽.
- НПА из xlsx: `https://docs.cntd.ru/document/1314770295` →
  **Постановление Правительства Москвы №3025-ПП от 09.12.2025** «Об установлении
  размеров отдельных социальных и иных выплат на 2026 год».
- Скормил текст этого документа `Classifier.explain()` напрямую (в обход обнаружения
  через листинг) — классификатор **корректно** пометил его релевантным (ЖС `disabled`
  по «инвалид», тематический блок по «выплата»/«компенсация»/«социальная поддержка»).
- Попробовал найти этот же документ через листинг `mos.ru` (единственный источник,
  где он теоретически мог бы всплыть) — не нашёл рабочий способ фильтрации по дате/
  номеру документа через query-параметры (`?query=`, `?dateFrom=`/`?dateTo=` — угаданы
  вслепую, сервер их проигнорировал, `totalCount` не изменился). У сайта в интерфейсе
  есть фильтры «диапазон дат (календарь)» и «поиск по номеру/названию» (см.
  `docs/STAGE0.md` раздел 2, находки по `mos.ru`), но реальные имена параметров/формат
  запроса, которые использует фронтенд, не установлены — нужен отдельный разбор через
  devtools/network, не выяснено с ходу.

**Вывод на текущий момент:** классификатор («мозги») работает правильно на реальном
целевом документе; обнаружение через листинги («глаза») ограничено горизонтом в дни,
не месяцы — архитектурно, не баг. Полноценный ретроспективный бэктест этим путём
непрактичен.

## 3. Предлагаемая альтернатива — поиск через Yandex Search

Идея пользователя: вместо (или в дополнение к) постраничному обходу листингов —
поисковый запрос в Yandex Search с двумя фильтрами:
- **по периоду** (дата публикации в диапазоне);
- **по белому списку доменов** (`data/sources.yaml` + `data/regions.yaml` — тот же
  список, что уже используется для `parser/filters.py::is_domain_whitelisted`, через
  `site:` или аналогичный оператор, либо пост-фильтрацию результатов).

**Уже есть на что опереться — не с нуля:**
- `/Users/user/dev/auto/.env` содержит `YANDEX_SEARCH_API_KEY`/`YANDEX_SEARCH_FOLDER_ID`
  — то есть в соседнем проекте это уже настроено и, видимо, использовалось (нужно
  проверить, для чего именно и работают ли креды сейчас).
- `measure_deepagent` (независимый репозиторий, обзор — `docs/STAGE0.md` раздел 1) —
  там есть `revision_agent/npa_search.py`, `search_searxng.py`,
  `npa_fetcher.py::search_and_fetch_npa`: полнотекстовый поиск НПА по allowlist-доменам
  через Yandex Search API **или** self-hosted SearXNG, с ранжированием по домену и
  фоллбэком на первый подходящий результат. При обзоре 2026-08-19 сознательно не взяли
  в переиспользование, т.к. на тот момент задача была другая (обход известных
  листингов, не поиск по названию/периоду) — этот вывод стоит пересмотреть именно для
  сценария «поиск за период», а не для ежедневного обхода.

## 4а. Проверено вживую 2026-08-20 — ответы на пункты раздела 4

Все живые вызовы делались напрямую к
`POST https://searchapi.api.cloud.yandex.net/v2/web/search` с кредами из
`/Users/user/dev/auto/.env`, без промежуточного кода — только чтобы закрыть открытые
вопросы перед реализацией.

1. **Креды актуальны.** `YANDEX_SEARCH_API_KEY`/`YANDEX_SEARCH_FOLDER_ID` из
   `/Users/user/dev/auto/.env` (folder `b1gplve2ue70hj8270mh`) дают `HTTP 200` прямо
   сейчас. Заводить новые/отдельные для этого проекта не нужно — копировать эти же в
   `.env` этого репозитория (как уже и предполагалось, AGENTS.md раздел 16 п.9).

2. **Формат периодного фильтра — решён.** У `queryText` есть оператор
   `date:YYYYMMDD..YYYYMMDD`, работает как точный диапазон (подтверждено: запрос с
   заведомо будущим диапазоном `date:20990101..20990110` вернул `error code="15"
   Искомая комбинация слов нигде не встречается` вместо ~1 млн хитов без фильтра —
   значит оператор реально применяется, а не игнорируется). Отдельно есть top-level
   поле запроса `period` (proto-enum) — перебором подобраны рабочие значения
   `PERIOD_ALL_TIME` / `PERIOD_MONTH` / `PERIOD_DAY` / `PERIOD_UNSPECIFIED` (`PERIOD_YEAR`/
   `PERIOD_WEEK`/`PERIOD_HALF_YEAR` — 400, невалидны), но это грубый относительный
   фильтр («последний месяц/день»), не произвольный диапазон — **для ретроспективного
   поиска использовать `date:` в `queryText`, не `period`.**

3. **Домен-фильтр — решён, пост-фильтрация не нужна.** `site:d1 | site:d2 | …` внутри
   `queryText` (та же схема, что в `measure_deepagent/revision_agent/npa_search.py`)
   отработал на всех 14 доменах из `data/sources.yaml`/`data/regions.yaml`
   одновременно, без ошибки и без обрезания — лимита на число `site:`-условий на этом
   масштабе не обнаружено. Значит фильтрация по белому списку доменов задаётся прямо в
   запросе, отдельная пост-фильтрация выдачи не требуется.

4. **Ревью `measure_deepagent` — сделано.** `revision_agent/npa_search.py`

   API v2 контракт (base64+XML в `rawData`, `Api-Key` заголовок, те же env-переменные).
   Вердикт: **переиспользовать паттерн (эндпоинт, форма запроса, разбор base64/XML,

## 4б. Найдено и исправлено вживую 2026-08-20 — реальный лимит на число документов

При первом пробном прогоне (поиск за 3 месяца по каждой из трёх ЖС, 100 доменов ×
запрошенный `resultsCount=100`) реально возвращалось **всегда ровно 10 документов**,
независимо от `resultsCount`. Проверка (`curl` с `page=0` и `page=1` — оба вернули
идентичный набор из 10 URL) показала, что и `resultsCount`, и top-level `page` из
первой версии (`search_yandex`) сервер молча игнорировал.

Причина найдена в открытых protobuf-определениях API
(`github.com/yandex-cloud/cloudapi`, файл
`yandex/cloud/searchapi/v2/search_service.proto`, публичный репозиторий, не требует
доступа — документация на `aistudio.yandex.ru` за капчей, а исходники протокола нет):
- `resultsCount` — этого поля нет в `WebSearchRequest` вообще. Референсные реализации
  (`measure_deepagent/revision_agent/npa_search.py`, исторический
  `auto/revision_agent/yandex_search.py`) его тоже передают — вероятно, скопировано из
  устаревшей документации/более раннего API, сервер такие лишние поля просто не
  применяет, не отвечает ошибкой.
- Реальный лимит — `GroupSpec.groups_on_page` (1–100), внутри `groupSpec`. По умолчанию
  `GroupSpec.group_mode = GROUP_MODE_DEEP` — группировка по домену, **1 документ на
  домен на страницу**, отсюда и «всегда 10» (по числу доменов в топе выдачи). Нужен
  `group_mode = GROUP_MODE_FLAT`, чтобы получать документы одним списком без обрезания
  по домену.
- Страница задаётся `query.page` (вложено в объект `query`, не top-level `page`) —
  проверено: `query.page=1` реально даёт другую страницу выдачи (другой набор URL),
  top-level `page` эхо в ответе всегда показывал `0`.

Проверено вживую: тот же запрос (инвалиды, 3 месяца, весь белый список) с
`groupSpec: {groupMode: GROUP_MODE_FLAT, groupsOnPage: 100}` вернул 100 документов
вместо 10, релевантных стало 38 вместо 5. Исправлено в `parser/discovery_search.py`
(`search_yandex`/`run_discovery_search`, параметр `max_pages` — реальная пагинация
через `query.page`, с ограничением по числу платных вызовов за прогон). Тесты
обновлены (`tests/test_discovery_search.py`), включая тест на пагинацию.

## 5. Встраивание в ежедневный прогон — решено и реализовано 2026-08-20

Пользователь подтвердил: биллинг Яндекса для проекта не критичен, включаем Yandex
Search и для ежедневного обновления, не только для ретроспективного бэктеста
(закрывает пункты 5–6 раздела 4).

**Архитектурное решение:** не `SourceSpec`/`process_source` в `orchestrator.py`.
Причина — несовпадение формы: `process_source` вычисляет окно поиска (`window_start`)
только для того, чтобы знать, когда остановить постраничный обход (сравнивает
`published_at` каждой публикации с окном, листинг сам по себе окна не знает и не
использует). Yandex Search устроен наоборот — диапазон дат нужен *до* вызова API, он
часть текста запроса (`date:YYYYMMDD..YYYYMMDD`), и `published_at` у найденных
документов всегда `None` (раздел 4а — ненадёжен). Поэтому реализовано отдельной
функцией:

- `parser/discovery_search.py::run_daily_discovery(session, classifier, *, api_key,
  folder_id, life_situations=None, ...)` — по умолчанию берёт ЖС из
  `db.catalog.load_life_situations()` (`data/life_situations.yaml`, без хардкода — новая
  ЖС в справочнике подхватывается сама, AGENTS.md раздел 1). На каждую ЖС:
  - свой ключ окна доверстывания `yandex_search:<id>` через уже существующий
    `parser/state.py` (`fetch_window_start`/`mark_source_processed`) — тот же механизм
    «искать не жёстко за сутки, а с даты последнего успешного обхода», что и у
    листинговых источников (AGENTS.md раздел 4);
  - запрос строится из `situation.keywords`, обрезанных под лимит API в 400 символов на
    `queryText` (`_bounded_keywords_query` — сам site:-фильтр по 14 доменам уже занимает
    больше половины лимита, для ЖС с длинным списком фраз, как «инвалиды», урезание
    реально включается);
  - сбой одной ЖС (сеть, лимит API — `YandexSearchUnavailable`, либо любая другая
    ошибка) не прерывает обход остальных ЖС и не сдвигает её собственное окно
    доверстывания — тот же принцип изоляции, что у `process_source`
    (AGENTS.md раздел 12); коммит после каждой ЖС.
- Вызывается из `parser/__main__.py` после `run_all()`, только если в `.env` заданы
  `YANDEX_SEARCH_API_KEY`/`YANDEX_SEARCH_FOLDER_ID` — иначе шаг молча пропускается
  (WARNING в лог), не блокирует обычный суточный прогон листингов.

**Проверено вживую 2026-08-20** на изолированной БД (не боевой dev-базе): первый
прогон (пустая БД) взял стандартное окно первого запуска в 7 дней на каждую из 3 ЖС,
создал 28 сигналов суммарно (кросс-ЖС дедуп по URL сработал — часть найденного по
«инвалидам» и «СВО» пересекалась). Второй прогон день спустя показал окно
`date:20260820..20260821` — с даты последнего успешного прогона первой ЖС, не заново
7 дней назад — доверстывание по каждой ЖС работает как и было спроектировано.

Тесты (`tests/test_discovery_search.py`): создание сигнала с per-ЖС `source_key`,
доверстывание окна между прогонами, изоляция сбоя одной ЖС от остальных, усечение
запроса под лимит API. `tests/test_parser_main.py`: `python -m parser` вызывает
`run_daily_discovery` только когда заданы креды, и не вызывает, когда их нет —
понадобилось после того, как первая версия тестов `parser/__main__.py` без мока
`run_daily_discovery` реально дозвонилась до Yandex Search при каждом прогоне тестов
(в `.env` лежат настоящие креды) — 9 секунд вместо 0.3 на 2 теста, обнаружено по
времени выполнения.
