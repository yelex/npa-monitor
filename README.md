# npa-monitor

Мониторинг изменений в НПА (нормативно-правовых актах) по мерам поддержки для
ветеранов боевых действий, людей с инвалидностью и участников СВО. Полный контекст
требований и архитектурные решения — [AGENTS.md](AGENTS.md), план и чек-лист по
фазам — [PLAN.md](PLAN.md).

## Структура

- `db/` — модели SQLAlchemy 2.0, слой сервисов (переходы статусов, дедуп), SQLite WAL.
- `parser/` — ежедневный сборщик публикаций (`sources/` — адаптеры под источники).
- `bot/` — Telegram-бот, интерфейс эксперта.
- `data/` — справочники (ЖС, регионы, белый список источников) — данные, не код.
- `docs/` — исходные требования, xlsx-примеры карточек мер, `STAGE0.md`
  (диагностика источников/сети).
- `tests/` — юнит-тесты.

## Разработка

Требуется Python ≥3.10.

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -e ".[dev]"
```

Переменные окружения — скопировать `.env.example` в `.env` и заполнить реальными
значениями (файл `.env` не коммитится, см. `.gitignore`).

```bash
cp .env.example .env
```

### Тесты и линтер

```bash
pytest
ruff check .
```

### Запуск бота

Нужен как минимум `TELEGRAM_BOT_TOKEN` и `ALLOWED_TELEGRAM_USER_IDS` в `.env`.

```bash
python -m bot
```

БД (SQLite) создаётся автоматически по пути `DATABASE_PATH` (по умолчанию
`data/npa_monitor.db`) при первом запуске.

Утренняя сводка (~08:00) рассылается самим ботом в фоне, пока он запущен (`_digest_loop`
в `bot/main.py`) — отдельно ничего планировать не нужно.

### Запуск парсера

Один прогон по всем источникам, не демон — планируется извне (AGENTS.md раздел 14:
ежедневно в 06:00).

```bash
python -m parser
```

`-v`/`--verbose` — подробный трейс по каждой публикации: какие ключевые слова ЖС/
тематического блока совпали (или нет), почему релевантно/не релевантно, тип события,
регион, приоритет, и если создан сигнал — его id. Без сторонних DEBUG-логов (httpx и
т.п. остаются на INFO).

```bash
python -m parser -v
```

Пример строки лога:
```
DEBUG:parser.orchestrator:публикация: 'Более 15 тысяч людей с инвалидностью получили компенсацию по ОСАГО' (...)
DEBUG:parser.orchestrator:  ЖС: disabled (по 'инвалид') | тематический блок: да ('компенсация') | РЕЛЕВАНТНО | тип события: review; регион: rf; приоритет: low
DEBUG:parser.orchestrator:  -> сигнал создан, id=7
```

Без Docker (см. ниже) — пример строки `crontab -e` (venv в `/opt/npa-monitor/.venv`,
проект в `/opt/npa-monitor`):

```cron
0 6 * * * cd /opt/npa-monitor && .venv/bin/python -m parser >> /var/log/npa-monitor-parser.log 2>&1
```

Если в `.env` заданы `YANDEX_SEARCH_API_KEY`/`YANDEX_SEARCH_FOLDER_ID`, после обхода
листингов автоматически идёт ещё один проход — по одному поисковому запросу на каждую
ЖС из `data/life_situations.yaml` через Yandex Search (docs/SPEC_yandex_search_discovery.md,
раздел 5). Окно поиска — с даты последнего успешного прогона этой ЖС (то же
доверстывание, что и у листинговых источников, `parser/state.py`), не обязательно
последние сутки. Не задан ключ — шаг молча пропускается (не обязательное условие
готовности, AGENTS.md раздел 15). У каждой ЖС свой источник-ключ
(`yandex_search:<id>`), поэтому сбой поиска по одной ЖС (сеть, лимит API) не мешает
остальным и не сбивает их окно.

### Ретроспективный поиск за период

Обход листингов (`python -m parser` выше) видит только последние дни — не годится для
поиска НПА за прошлые месяцы (например, для бэктеста классификатора). Отдельный
инструмент — поиск через Yandex Cloud Search API по белому списку доменов и диапазону
дат, не часть ежедневного прогона (docs/SPEC_yandex_search_discovery.md). Требует
`YANDEX_SEARCH_API_KEY`/`YANDEX_SEARCH_FOLDER_ID` в `.env` (см. `.env.example`).

```bash
python -m parser.discovery_search --from 2025-12-01 --to 2025-12-31 \
  --query "постановление социальные выплаты" --dry-run -v
```

Без `--dry-run` найденные релевантные публикации создают сигналы в общей БД (дедуп по
URL — общий с ежедневным обходом, повторных сигналов не будет). `--domains` сужает
поиск до подмножества доменов через запятую (по умолчанию — весь белый список
`data/sources.yaml`+`data/regions.yaml`). `--results-count` — документов на страницу
выдачи (макс. 100), `--max-pages` — сколько страниц запросить (каждая страница сверх
первой — отдельный платный вызов API, по умолчанию 1).

## Деплой

AGENTS.md раздел 12: свой сервер/VPS, Docker. Один образ (`Dockerfile`) на `parser` и
`bot` — общий код и зависимости, `docker-compose.yml` разводит их по сервисам с разными
`command`.

```bash
cp .env.example .env   # заполнить реальными значениями
docker compose build
docker compose up -d bot   # долгоживущий процесс: polling, утренняя сводка
```

`parser` — **не демон**, не поднимается автоматически с `up` (см. `profiles: ["cron"]`
в `docker-compose.yml`), запускается по расписанию извне:

```cron
0 6 * * * cd /opt/npa-monitor && docker compose run --rm parser >> /var/log/npa-monitor-parser.log 2>&1
```

(эквивалент — systemd timer: юнит с `ExecStart=docker compose run --rm parser` +
`OnCalendar=*-*-* 06:00:00`, если на сервере принято systemd вместо cron).

БД — именованный volume `npa_data` (`/app/data` в контейнере, путь внутри —
`DATABASE_PATH` из `.env`), переживает пересборку образа и перезапуски контейнеров.

**RU-прокси для RSNET-доменов** (`publication.pravo.gov.ru`/`kremlin.ru`/
`government.ru`, docs/STAGE0.md раздел 2.1) — `RU_PROXY_URL` в `.env`. IP боевого VPS
должен быть в allow-листе прокси-сервера (это отдельный, внешний сервер, не часть
`docker-compose.yml`) — **это единственный пункт, который нельзя проверить из образа
самого по себе**, нужно подтвердить именно с боевого VPS после разворачивания
(проверено 2026-08-20 с другой машины после добавления её IP в allow-лист — см.
AGENTS.md раздел 16 п.7 — сам прокси и код клиента рабочие, вопрос только в allow-листе
для конкретного IP сервера).

Проверено вживую при подготовке Фазы 7 (2026-08-20): образ собирается, `bot`
корректно падает с понятной ошибкой при отсутствии `TELEGRAM_BOT_TOKEN`, `parser`
реально обходит источники и создаёт сигналы внутри контейнера, БД переживает
перезапуск контейнера с тем же volume. CI (`.github/workflows/ci.yml`) на каждый push
дополнительно проверяет, что образ собирается и это поведение не ломается.
