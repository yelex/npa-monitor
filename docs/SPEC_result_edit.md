# Спека: редактирование/удаление полей результата агента автообновления

Статус: **черновик (2026-08-27), не реализовано** — записано по запросу Алексея.
Связанные: SPEC_autoupdate_agent_contract.md (3.4 контракт результата),
SPEC_result_card_split.md (доставка карточки).

## 1. Контекст

Результат агента (`results/<task_id>.json`, спека 3.4) доставляется аналитику
карточкой в TG; после проверки аналитик делает `/complete`. Контракт результата —
плоский: `status`, `summary`, `details`. Результат живёт только в файле
`results/.processed/<task_id>.json`, в БД не попадает.

## 2. Проблема

Аналитик может принять результат **с поправками** (в summary/details ошибка,
опечатка, лишний фрагмент) или принять только часть (удалить неверное поле).
Сейчас единственное действие — `/complete`: поправить, удалить поле или сохранить
правку негде — отредактированный аналитиком вариант нигде не фиксируется.

## 3. Предлагаемое решение (MVP)

### 3.1 Персистентность: результат → БД

Новая таблица `signal_results` (SQLite, миграция через `db/session.py::
_ensure_columns`-паттерн или `CREATE TABLE IF NOT EXISTS` при старте — по аналогии
с `DocumentSeen.title`):

- `id` PK, `signal_id` FK → signals (unique — один актуальный результат на сигнал,
  перезапись при новом результате)
- `payload_original` JSON — как пришло от агента (неизменяемый эталон)
- `payload_edited` JSON NULL — версия после правок аналитика (NULL = правок не было)
- `received_at`, `updated_at` UTC

Точка записи: `bot/main.py::scan_autoupdate_results` — после успешного чтения
payload, до отправки карточки (архивирование файла остаётся как есть).

### 3.2 Просмотр и правки (команды, MVP без inline-клавиатур)

- `/result <signal_id>` — показать карточку последнего результата сигнала
  (с пометкой «✏️ отредактировано», если есть `payload_edited`); если правок нет —
  как в оригинале. Пройдёт через `_split_message` (>4096).
- `/edit <signal_id> <field> <текст>` — заменить поле (`summary` или `status`;
  для `details` — reply-режим, см. ниже). Пишет в `payload_edited`, сохраняя
  остальные поля из оригинала.
- `/edit <signal_id> details` → бот просит прислать новый текст details следующим
  сообщением (details многострочный и длинный, в аргумент команды не влезает).
- `/del <signal_id> <field>` — удалить поле из результата (поле = null в
  `payload_edited`). `/del <signal_id> all` — сбросить все правки к оригиналу.

Разрешённые поля: `status`, `summary`, `details`. Прочее из payload — read-only.

### 3.3 Что видит потребитель

Карточка `/result` рендерит `payload_edited ?? payload_original`. Дальнейший
даунстрим (экспорт в knowledge base агента, отчёты) обязан читать отредактированную
версию — зафиксировать при проектировании экспорта (сейчас потребителя нет,
`/complete` меняет только статус сигнала).

### 3.4 Права и журналирование

- Только `allowed_user_ids` (как все команды бота).
- Каждая правка логируется (`log.info`, user_id) — аудит без отдельной таблицы
  версий; оригинал неизменен в `payload_original`.

## 4. Открытые вопросы (для Алексея)

1. Достаточно ли плоских полей `status/summary/details`, или агент скоро начнёт
   присылать структуру (меры по-отдельности) — тогда редактирование «по полям»
   нужно проектировать под вложенный diff. Предложение: MVP делать по текущему
   контракту, при расширении контракта — v2.
2. Нужен ли экспорт отредактированного результата (куда?) — сейчас после
   `/complete` данные никуда не идут.
3. Команды vs inline-кнопки на карточке — предложены команды (проще, details
   длинный); кнопки добавить позже поверх тех же функций.

## 5. Как воспроизвести проблему

1. Положить в `results/` JSON с `signal_id` существующего сигнала в статусе
   SENT_TO_AGENT.
2. Дождаться карточки (≤5 мин).
3. Попытаться поправить summary — механизма нет; `/complete` фиксирует лишь
   статус сигнала.
