# Спека (черновик): ложное «Ссылка недоступна» при приёме ссылки на НПА

Статус: **черновик, не реализовано**. Баг воспроизведён и локализован (раздел 3), причина
задокументирована в самом справочнике источников (раздел 3, `data/sources.yaml`), но фикс
не выбран окончательно — открытых вопросов (раздел 5) больше одного, нужно решение
пользователя перед реализацией.

## 1. Проблема

Эксперт получил ложный отказ на корректную ссылку на НПА в сценарии «✅ Взять в работу →
бот просит ссылку» (AGENTS.md раздел 10):

```
[20.08.2026 17:14] Ирина Мальцева (Сбер): Сигнал 6 в работе. Отправьте ссылку на НПА
(или 'skip', если она уже в карточке).
[20.08.2026 17:19] Ирина Мальцева (Сбер): https://docs.cntd.ru/document/408415942
[20.08.2026 17:19] Ирина Мальцева (Сбер): Ссылка недоступна. Проверьте её и отправьте
ещё раз. Или загрузите файл напрямую.
```

Ссылка синтаксически корректна, домен `docs.cntd.ru` в белом списке (см. `data/sources.yaml`,
группа `other`) — значит отказ произошёл не на проверке домена (`bot/main.py:525-529`), а на
проверке доступности страницы (`bot/main.py:532-538`). Это не разовый сбой сети: для
`docs.cntd.ru` он произойдёт **для любой ссылки, всегда** — см. раздел 3.

## 2. Где в коде

`bot/main.py::on_npa_link` (строки 510–539):

```python
if not is_domain_whitelisted(text, all_domains()):
    ...
try:
    fetch(text, access="direct")          # <-- access захардкожен
except SourceUnavailable:
    await message.answer("Ссылка недоступна. ...")
    return
```

Два независимых наблюдения:

1. `access="direct"` захардкожен — не читается ни из `db.catalog.Source.access` (по домену
   ссылки), ни из `config.get_settings().ru_proxy_url`, который `bot/main.py` уже импортирует
   и использует в других местах (строка 28, `get_settings`). Для доменов с
   `access: ru_proxy` (например, будущая ссылка на `publication.pravo.gov.ru` или
   `kremlin.ru`, они тоже в белом списке через `all_domains()` — `data/sources.yaml`) проверка
   доступности точно так же обречена падать, если бот выполняется не с IP, у которого есть
   прямой доступ к RSNET-доменам (см. AGENTS.md раздел 16 п.7 — сама эта проблема и её обход
   через `RU_PROXY_URL` уже описаны, просто не подключены в `on_npa_link`).
2. Для `docs.cntd.ru` конкретно ситуация хуже, чем «не тот access»: в `data/sources.yaml`
   (строки 47–53) домен размечен `access: unsupported` с явным комментарием:

   > обзоры изменений — сетевого доступа нет вовсе (таймаут, проверено вживую 2026-08-20),
   > известная проблема measure_deepagent: SSO-redirect-loop без cookie jar, нужен RU-прокси
   > с полноценным cookie jar

   То есть уже известно и задокументировано, что простым `httpx.Client(...).get(url)` этот
   домен не открывается **в принципе** — ни `access="direct"`, ни голый `access="ru_proxy"` без
   доработки (cookie jar) это не починят. `db.catalog.all_domains()` при этом сознательно
   включает домены с `access="unsupported"` в белый список (`db/catalog.py:139-141`, докстринг:
   «известные источники, даже если парсер их пока не обходит автоматически») — то есть
   `docs.cntd.ru` проходит проверку домена, но 100% случаев не проходит проверку доступности.

`docs.cntd.ru` — не экзотический домен: это стандартный формат ссылки на текст НПА в целевых
данных проекта (`docs/Для проверки обновления.xlsx`, поле «Ссылка на НПА»; тот же домен как
мотивирующий пример — `docs/SPEC_yandex_search_discovery.md`, раздел 2,
`docs.cntd.ru/document/1314770295`). Эксперт будет присылать такие ссылки регулярно, и по
текущему коду бот отклонит **каждую** — это не пограничный случай, а systematic false negative
для одного из самых вероятных источников ссылок на НПА.

## 3. Воспроизведение

```
$ curl -sv --max-time 15 "https://docs.cntd.ru/document/408415942"
# таймаут на установке соединения — совпадает с поведением RSNET-заблокированных
# доменов (kremlin.ru и т.п.) с не-РФ IP
```

Проверено 2026-08-20 с машины разработчика (не боевой VPS, без действующего доступа к
`RU_PROXY_URL` в моменте проверки — прокси `95.142.42.28:8888` тоже не ответил за то же время).
Это согласуется и с более ранней живой проверкой, зафиксированной в `data/sources.yaml`
(«сетевого доступа нет вовсе, таймаут, проверено вживую 2026-08-20»), и с диагнозом
measure_deepagent про SSO-redirect-loop. Отдельно стоит перепроверить с боевого VPS
(AGENTS.md раздел 16 п.7 — актуальность allow-листа прокси всё равно требует
переподтверждения) — но даже если прямой доступ с VPS частично работает, это не отменяет
находку п.2: `access="unsupported"` в справочнике был явно проставлен как «программно не
открывается», и код `on_npa_link` этот статус просто не читает.

## 4. Варианты решения

**Вариант A — не проверять доступность для доменов `access: unsupported`.**
Раз в справочнике уже зафиксировано «источник не обходится автоматически», `on_npa_link`
должен для таких доменов пропускать сетевую проверку и принимать ссылку на доверии (как если
бы эксперт прислал `skip`), с пометкой в ответе, что автопроверка недоступна — например:
«✅ Ссылка принята (домен docs.cntd.ru не поддерживает автопроверку, проверьте вручную).
Статус: Передан агенту.» Минимальное изменение, ничего не чинит в самом фетче, но убирает
100%-й false negative уже сегодня.

**Вариант B — довести access до рабочего состояния (cookie jar + RU-прокси) и переключить
`docs.cntd.ru` на `ru_proxy`.**
Решает точнее (настоящая проверка доступности вместо доверия), но требует:
- доработки `parser/fetcher.py` — `httpx.Client` уже держит cookie jar в рамках одного
  `with` (он и сейчас использует `httpx.Client(...)`, не `httpx.get`), но SSO-редирект может
  требовать нескольких раундов/страниц до простановки нужных cookie — нужно перепроверить
  вживую, что именно ломается, а не просто сменить access в yaml;
- рабочего `RU_PROXY_URL` в окружении, где крутится бот (см. раздел 3 — на момент этой
  проверки прокси недоступен даже с той машины, где он раньше был в allow-листе).
Дороже, но закрывает проблему по существу и для парсера тоже (сейчас `docs.cntd.ru` не
обходится вообще, только `/comments` числится источником).

**Вариант C — общий фикс п.1 (не хардкодить `access="direct"`) + вариант A для `unsupported`.**
Даже если оставить `docs.cntd.ru` как «недоступен для проверки» (вариант A), стоит отдельно
починить то, что `on_npa_link` игнорирует `access`/`RU_PROXY_URL` для доменов `ru_proxy` —
иначе тот же баг всплывёт на следующей ссылке с `publication.pravo.gov.ru`/`kremlin.ru`,
просто позже. Нужен помощник в `db/catalog.py` — что-то вроде `access_for_domain(domain) ->
str | None` по данным `load_sources()`/`load_regions()` (сейчас `all_domains()` отдаёт только
плоский `set[str]`, access теряется), и передача `ru_proxy_url=get_settings().ru_proxy_url`
в `fetch(...)`, когда `access == "ru_proxy"`.

**Рекомендация:** C — закрывает и конкретный репорт (`docs.cntd.ru`), и тот же класс бага для
`ru_proxy`-доменов, без того, чтобы сейчас чинить SSO-redirect-loop (вариант B можно сделать
отдельной, более поздней задачей, если окажется, что доверие к `unsupported`-ссылкам
неприемлемо для заказчика).

## 5. Открытые вопросы

1. 🔴 Приемлемо ли для заказчика принимать ссылку на `unsupported`-домен без автопроверки
   (вариант A/C), или обязательна именно сетевая проверка перед «Передан агенту» — нужно
   решение пользователя, в ТЗ (`docs/Требования_к_мониторингу_изменений_в_НПА.html`) этот
   случай не разобран отдельно.
2. 🔴 Стоит ли вкладываться в вариант B (cookie jar/SSO для `docs.cntd.ru`) сейчас или
   отложить — зависит от того, насколько часто реально приходят ссылки именно на этот домен
   (весь целевой xlsx использует его как основной источник ссылок на НПА, см. раздел 2).
3. 🟡 Актуальность `RU_PROXY_URL`/allow-листа прокси на момент реализации — перепроверить с
   боевого VPS перед тем, как полагаться на `ru_proxy` для любого домена в `on_npa_link`
   (тот же открытый пункт, что и AGENTS.md раздел 16 п.7).

## 6. Черновой план реализации (вариант C)

1. `db/catalog.py` — добавить `access_for_domain(domain: str, sources=None, regions=None) ->
   str | None`, возвращающий `Source.access` по точному/поддоменному совпадению (та же логика
   совпадения, что в `parser/filters.py::is_domain_whitelisted`, но с сохранением access, а не
   только bool).
2. `bot/main.py::on_npa_link` — заменить блок доступности:
   - определить `access = access_for_domain(domain_of(text))`;
   - если `access == "unsupported"` — пропустить сетевую проверку, принять ссылку с пометкой
     в тексте ответа;
   - иначе вызвать `fetch(text, access=access, ru_proxy_url=get_settings().ru_proxy_url if
     access == "ru_proxy" else None)`.
3. Тесты — `tests/test_bot_main.py` (секция «on_npa_link: белый список домена + проверка
   доступности», строки ~435+): добавить кейсы на `access="unsupported"` (доверие без сетевого
   вызова — assert `fetch` не вызван) и на `access="ru_proxy"` (assert `fetch` вызван с
   `ru_proxy_url` из `get_settings()`), плюс тест на `db.catalog.access_for_domain`
   (`tests/test_catalog.py`, если файл уже есть — проверить).
4. Обновить `README`/`AGENTS.md`, если по итогам открытого вопроса 1 поведение бота для
   `unsupported`-доменов фиксируется как окончательное (не временное).
