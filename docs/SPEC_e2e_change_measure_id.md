# SPEC: E2E ветки change + measure_id (Фаза 12, «следующий шаг»)

Статус: ревью Клода учтено (2026-08-27: реальные команды бота, полный FSM-порядок шагов, риск ветки отказа), к исполнению.

## Контекст

Первый E2E коннектора (2026-08-25, `SPEC_connector_deploy_e2e.md` в npa-somas)
замкнул только ветку `new` (measure_id=null): sig-108 → done, sig-106 →
nothing_found, карточки дошли до аналитика в TG. Ветка **change + measure_id**
(полевой дифф «было → стало» против benefits_knowledge_base) в бою не
проверялась — не было живой задачи через новый флоу Фазы 12
(сигнал → «Изменение» → саджест мер → выбор).

Всё уже реализовано и покрыто тестами:
- бот: FSM-шаги типа сигнала и выбора меры (`docs/SPEC_signal_type_measure_select.md`,
  коммит ade86f8), задача v2 в spool;
- коннектор npa-somas v3.1: change → KB-запись по measure_id → экстракция
  SO-MAS → `select_benefit_card` → `field_diff` → result (спека
  `docs/specs/npa-monitor-spool-connector.md`, деплой —
  `SPEC_connector_deploy_e2e.md`);
- бот: `_results_scan_loop` (300 с) → карточка `result_card` → архивирование.

Проблема: нет подтверждения, что цепочка целиком работает на проде — от клика
аналитика до карточки с диффом в TG.

## Предполагаемый сценарий (два прогона)

### Прогон A — пре-чек меры без бота (отладочный)

Цель: убедиться, что выбранная мера вообще даёт осмысленный дифф (акт фетчится,
экстракция находит карточку), ДО того как аналист потратит время на флоу.
Инструмент уже есть: `--measures` в CLI коннектора (`_run_measures_debug`,
прогон без спула, act по НПА из golden_standard.json).

1. Короткий список кандидатов: 2–3 московские меры с известными суммами
   (например 00_svo_*, 77_vbd_*), федеральные акты — приоритет (pravo.gov.ru
   через RU-прокси работает).
2. `docker run --rm --env-file /opt/npa-somas/.env.docker npa-somas-connector:latest
   --measures <id1>,<id2>...`
3. Критерий: хотя бы одна мера → `done` с непустым диффом. Её и берём в прогон B.

### Прогон B — живой E2E через бота

1. Аналитик (Алексей) в TG берёт один сигнал в работу: `/today` или `/pending` →
   inline-кнопка «✅ Взять в работу» (`sig:<id>:work`) на карточке. Затем полный
   FSM-флоу: ввод НПА-ссылки → подтверждение ЖС (`catc:`) → подтверждение региона
   (`reg:`/`regletter:`) → тип сигнала → выбор меры. На шаге НПА-ссылки указываем
   **акт из KB-записи выбранной меры** (или реальный свежий сигнал, если он по
   факту меняет известную меру — тогда мера выбирается из саджеста честно).
2. Шаг типа: «Изменение» → саджест мер (топ-8, пагинация/ручной ввод) →
   выбрать нужную меру → «Передать агенту».
3. Проверить: `tasks/sig-<id>.json` в spool — schema_version=2, signal_type=change,
   measure_id заполнен, measure_row_hash совпадает с KB (row_hash).
4. Запустить коннектор на проде (команды — SPEC_connector_deploy_e2e.md):
   `docker run --rm --name npa-connector-e2e -v npa-monitor_npa_data:/spool
   --env-file /opt/npa-somas/.env.docker npa-somas-connector:latest
   --spool-dir /spool/autoupdate_spool --limit 1`
5. Результат: карточка в TG со статусом и диффом (было → стало), сигнал в
   SENT_TO_AGENT; аналитик выполняет `/complete <id>`.
6. `results/.processed/` содержит архив, `tasks/.claimed/` пуст.

## Критерии готовности

- [ ] Прогон A: выбрана мера с `done` и непустым диффом.
- [ ] Прогон B: задача v2 (change + measure_id + row_hash) реально записана
      ботом в spool через FSM-флоу (не руками).
- [ ] Коннектор вернул `done`; в details — дифф по полям (сумма/условия).
- [ ] Карточка доставлена аналитику в TG автоматически (в пределах 5 мин).
- [ ] `/complete` отработал, сигнал → COMPLETED.
- [ ] `.claimed/` пуст, результат в `.processed/`.

## Что НЕ входит

- Включение cron коннектора (отдельное решение после подтверждения карточек).
- Retry/error-алертинг коннектора.
- Правки экстракции/матчинга — если дифф пустой или кривой, это отдельный тикет
  в npa-somas, не блокер E2E-транспорта (сам факт done+дифф = транспорт работает).

## Риски / заметки

- **Ветка отказа коннектора:** при `error`/`nothing_found` сигнал остаётся в
  SENT_TO_AGENT навсегда — обратного авто-перехода нет. Для E2E это означает:
  если прогон A не дал ни одной меры с `done`, прогон B не начинать (выбрать
  другую меру/акт), иначе сигнал придётся снимать вручную. Общий фикс
  (retry/возврат в работу) — отдельный тикет, вне скоупа.
- GigaChat 429/таймауты — уже наблюдалась ретраями в первом E2E, не блокер.
- Сигналов с осмысленным npa_link в боевой БД сейчас мало (последние NEW без
  ссылки — она вводится аналитиком на шаге флоу), поэтому прогон B
  рассчитан на ручной ввод ссылки аналитиком.
- Если саджест не находит меру по названию — есть ручной ввод measure_id
  (фича Фазы 12), это тоже часть проверки.
