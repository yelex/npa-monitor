# AGENTS.md — Система мониторинга изменений в НПА (меры поддержки)

> Постоянный контекст проекта. Часть более крупной инициативы «Агент автообновления» —
> здесь описан только контур **обнаружения и сигнализации об изменениях в НПА**, а не сам
> экстрактор карточек мер.

---

## 1. Цель

Автоматизировать ежедневный мониторинг публикаций о принятии, изменении или отмене
нормативных документов по трём жизненным ситуациям (ЖС) и обеспечить передачу
релевантных НПА эксперту (аналитику) на изменение данных после ручного подтверждения.

**ЖС в скоупе:**
1. Ветераны боевых действий (ВБД)
2. Люди с инвалидностью
3. Участники СВО и члены их семей

**MVP-периметр:** только Москва (77) + федеральный уровень, где применимо (аналогично
листам `Инвалиды 2025/2026`, `ВБД 2025/2026`, `СВО 2025/2026` в
`Для_проверки_обновления.xlsx`). Расширение на 89 регионов — после пилота.

Источник требований: `Требования_к_мониторингу_изменений_в_НПА.html`.
Пример целевых данных (полей карточки меры) и before/after 2025→2026: `Для_проверки_обновления.xlsx`.
Методика `Методика_и_критерии_оценки_качества_извлечения_данных.docx` — **отдельный контур**
приёмки качества работы агента-экстрактора карточек (Recall/Precision/QS). К мониторингу
изменений НПА относится только справочно, в этом проекте не реализуется, но схема полей
карточки меры (measureId, measureTerms, measureSum, categoryMobilized и т.д.) — общий
словарь данных для обеих систем.

---

## 2. Роли

| Роль | Кто | Функция |
|---|---|---|
| Парсер | сервис (cron) | ежедневно обходит источники, находит публикации, формирует сигнал |
| Бот | Telegram-бот | интерфейс эксперта: карточки сигналов, команды, сводки |
| Эксперт (аналитик) | 1 человек | изучает сигнал, отбирает релевантные, отправляет ссылку на НПА агенту |
| Агент автообновления | LLM-агент (внешний по отношению к этому контуру) | получает ссылку на НПА от эксперта, извлекает изменения, обновляет карточку меры; результат по этому сигналу возвращается эксперту на финальную проверку |

Разграничение прав по регионам/категориям — не требуется в MVP (эксперт один).

---

## 3. Технологии

- Python + cron + Docker на VPS.
- Telegram Bot API (интерфейс эксперта: карточки, инлайн-кнопки `✅/❌/↩️`, команды).
- За основу поиска мер можно взять существующий проект:
  `https://github.com/yelex/measure_deepagent.git` (сеть в этой сессии недоступна —
  проверить/склонировать репозиторий на этапе реализации, оценить, что можно переиспользовать
  для парсинга/поиска мер).
- Отдельная БД для сигналов (очередь `/pending`, история `/history`), схема полей — по
  бизнес-требованию (см. раздел 7 ниже). Плюс связь «сигнал → measureId» для меры, которую
  он затрагивает (заполняется/подтверждается экспертом вручную).

## 4. Источники и парсинг

**Белый список источников** (см. п.4 требований):
- Федеральные: `publication.pravo.gov.ru`, `kremlin.ru`, `government.ru`, `sfr.gov.ru`,
  `mintrud.gov.ru`.
- Региональные (Москва в MVP): официальный портал правительства региона, сайт
  регионального минтруда/соцзащиты, портал правовой информации региона (если есть),
  официальный сайт главы региона.
  - Список ссылок по всем 89 регионам можно спарсить с
    `http://pravo.gov.ru/links/region/` — держать как справочник для будущего расширения
    за пределы Москвы.
- Иные (для контекста, не как основание для сигнала без подтверждения): `garant.ru`,
  `consultant.ru`, `docs.cntd.ru/comments`, `tass.ru`, `ria.ru`.

**Задача парсера — только найти сами нормативные акты** (ссылку на публикацию/НПА,
дату, тип и т.п.) и отдать их на дальнейший разбор; извлечение содержания и заполнение
карточки меры делает уже эксперт/агент автообновления за пределами этого парсера.

**Формат документов:** HTML-страницы публикаций и PDF (многие НПА приложены как PDF) —
нужна поддержка обоих. OCR — по необходимости, если PDF без текстового слоя (уточнить
на этапе реализации по фактическим примерам).

**Определение новизны публикации:**
- Основной критерий — дата публикации на самом источнике (сравнение с датой последнего
  успешного обхода / с последней увиденной датой по этому источнику).
- Дополнительно — смысловая валидация: с какой даты фактически вступает/действует
  изменение (дата в тексте акта может отличаться от даты публикации на портале) —
  это сверяется по содержанию, не только по метаданным листинга.
- Дедупликация: если публикация уже была обработана (по URL/ID документа) — новая
  карточка не создаётся (п.10 требований, «Публикация уже обработана»).

## 5. Расписание (уточнено с заказчиком)

- **06:00** — ежедневный обход источников парсером (это верное время; в исходном
  документе есть расхождение 06:00 vs 09:00 — зафиксировано здесь как решённое: 06:00).
- **~08:00** (через ~2 часа после парсинга) — бот присылает эксперту сводку по найденным
  сигналам.
- **Доверстывание пропусков:** если обход в какой-то день не состоялся (сбой), при
  следующем успешном запуске парсер обязан пройтись и по пропущенному периоду
  (не терять сигналы), а не только «за последние 24 часа». Логика: хранить дату
  последнего успешного обхода per-источник и от неё вести окно поиска, а не жёстко
  «today only».

## 6. Статусная модель сигнала

Из требований (п.7–8), статусы: **Новый → В работе → Отложен / Отклонён / Передан
агенту → Завершён**.

| Статус | Кто присваивает | Когда | Действия эксперта |
|---|---|---|---|
| Новый | Парсер | сигнал создан, эксперт ещё не отреагировал | ✅ Взять в работу / ❌ Отклонить |
| В работе | Эксперт | нажал «Взять в работу» | изучает сигнал, должен принять решение |
| Отложен | Эксперт | ↩️ «Позже» | возвращается в очередь `/pending` и в следующую сводку |
| Отклонён | Эксперт | ❌ «Отклонить» + причина | обязательна причина из списка (см. ниже) или «Другое» |
| Передан агенту | Эксперт | ✅ подтвердил релевантность | ссылка на НПА уходит агенту автообновления, привязывается к measureId |
| Завершён (конечный статус) | Эксперт | после проверки результата агента | сигнал уходит в `/history`, дальнейших действий не требует |

**Причины отклонения** (п.8 требований): «Не относится к целевым категориям»,
«Дубликат», «Не является НПА», «Другое».

---

## 7. Карточка сигнала — поля

Из п.7 требований:
- ID
- Категория (одна или несколько ЖС: ВБД / Инвалиды / СВО)
- Тип события: новый документ / изменение / отмена / вступление в силу / обзор
- Приоритет: высокий / средний / низкий
- Название документа (если извлечено)
- Реквизиты (если извлечены)
- Регион действия: «РФ» / конкретный субъект РФ / «Не определён»
- Ссылка на публикацию
- Дата и время создания
- Статус (см. раздел 6)

**Приоритизация** (п.5.1, эвристика):
- Высокий — прямое указание на ЖС + слова «новый / изменение / отмена / утратил силу /
  индексация / повышение» + есть ссылка на документ.
- Средний — косвенная связь с ЖС, нет ссылки на полный текст, или регион не определён.
- Низкий — аналитика, обзор, интервью без указания на конкретный документ.

**Ключевые слова по ЖС** (п.6.1, для классификации):
- ВБД: ветеран боевых действий, ВБД, ветеран СВО; люди с инвалидностью: инвалид,
  ребёнок-инвалид, лицо с ограниченными возможностями, инвалид с детства, инвалид по
  зрению; участники СВО: участник СВО, мобилизованный, контрактник, доброволец, члены
  семей участников СВО, дети участников СВО.
- Тематический блок мер поддержки: мера поддержки, выплата, льгота, пособие,
  компенсация, субсидия.
- Маркеры документа: «постановление», «указ», «закон», «приказ», «распоряжение».
- Маркеры сути: «принят», «утверждён», «подписан», «вступил в силу», «внесены изменения».

## 8. Словарь данных карточки меры (общий с методикой оценки, справочно)

Единая схема полей карточки меры (см. `Для_проверки_обновления.xlsx`), используется как
справочник для привязки сигнала к конкретной мере (не создаётся/не заполняется этим
контуром, только читается/связывается):

- **Общие:** measureId, region, measureName, measureSum / measure_first_group..
  measure_disabled_child, measurePeriodicity, measureTerms, department, measureType,
  measureLevel, Ссылка на источник, Ссылка на НПА (может быть несколько, с пунктом НПА),
  Признак индексации.
- **Инвалиды:** cause_general_disease, cause_war_trauma, cause_radiation,
  cause_disabled_child + суммы по группам инвалидности.
- **ВБД:** СategoryOfVeteran, ListOfDocuments, HowToApply, Link, Contacts, Категория
  льготы.
- **СВО:** categoryMobilized, categoryContractor, categoryVolunteer, kidsOfMilitary.

## 9. Команды бота

- `/today` — сигналы «Новый», «Отложен» за сегодня.
- `/pending` — все сигналы «В работе», «Отложен».
- `/history` — «Передан агенту» / «Завершён» / «Отклонён», последние 10.
- `/stats` — агрегированная статистика за неделю (по умолчанию).

Бот работает только с whitelisted Telegram ID эксперта(ов) (п.11, безопасность).
Сообщения от посторонних игнорируются. Все действия логируются. Передаваемые ссылки
проверяются на доступность домена (whitelist из раздела 4).

## 10. Happy Path (сквозной сценарий)

1. 06:00 — парсер обходит источники.
2. ~08:00 — бот присылает эксперту сводку.
3. Эксперт открывает сигнал → ✅ «Взять в работу».
4. Бот просит ссылку на НПА (если не извлечена автоматически).
5. Эксперт отправляет/подтверждает ссылку.
6. Бот передаёт ссылку и привязанный measureId агенту автообновления.
7. Агент обрабатывает НПА, возвращает результат.
8. Эксперт проверяет результат → сигнал переходит в «Завершён» → уходит в `/history`.

## 11. Граничные случаи (из требований)

**Парсинг:**
- Источник недоступен → 3 попытки, затем пропуск до следующего цикла (с сохранением
  «недообработанного» периода для доверстывания, см. раздел 5).
- Новых публикаций нет → бот отправляет «Новых сигналов нет».
- Публикация уже обработана → дубликат не создаётся (по URL/ID документа).

**Сссылка на НПА:**
- Ссылка недоступна → бот просит проверить и отправить ещё раз, либо загрузить файл
  напрямую.
- Если всё корректно → ✅ «Ссылка принята», статус → «Передан агенту».

**Бот:**
- Сигнал более 3 дней в статусе «В работе» → бот присылает напоминание.
- Эксперт отклонил сигнал → сигнал помечается и не возвращается.
- Эксперт нажал «Позже» → сигнал появится в следующей рассылке.

## 12. Открытые вопросы (для проработки на этапе реализации)

1. Точная схема служебной БД сигналов (таблицы/индексы) — предстоит спроектировать по
   полям из раздела 7, плюс `measureId` (nullable, FK) и `region` (для MVP всегда
   «Москва»/«РФ»).
2. PDF-парсинг: нужен ли OCR, или все целевые PDF содержат текстовый слой — проверить
   на реальных примерах после первых обходов источников.
3. Точный список источников по Москве (домены минтруда/соцзащиты Москвы, портал
   mos.ru и т.п.) — зафиксировать перед стартом парсера.
4. Логика определения даты «вступления в силу» отдельно от даты публикации — правила
   извлечения из текста акта (регулярные выражения / LLM-разбор) требуют отдельной
   проработки.
5. Возможность повторного открытия сигнала в статусе «Отклонён» (если эксперт ошибся) —
   не описана в требованиях, решить отдельно.
6. Как связан этот проект с репозиторием `measure_deepagent` — что переиспользуем
   (поиск мер / парсинг источников / инфраструктура), а что пишем заново — уточнить
   после ревью репозитория.
