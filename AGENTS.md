# Мониторинг изменений в НПА — контекст проекта

Система автоматизирует ежедневный мониторинг публикаций о принятии, изменении
или отмене нормативных документов по жизненным ситуациям (ЖС) и обеспечивает
передачу релевантных НПА на извлечение данных после ручной верификации
экспертом.

Источники требований:
- `docs/Требования_к_мониторингу_изменений_в_НПА.html` — полное ТЗ (разделы
  1–12 воспроизведены ниже).
- `docs/Для проверки обновления.xlsx` — примеры уже собранных мер поддержки
  (6 листов: Инвалиды/ВБД/СВО × 2025/2026) — это целевая структура данных,
  которую производит внешний «агент автообновления».

Это greenfield-проект: на момент написания файла в репозитории есть только
`docs/`. Ниже — весь функциональный контекст из ТЗ плюс архитектурные решения,
принятые с пользователем. Ничего из этого не выводится из кода — код ещё не
написан, поэтому этот файл является источником истины до появления реализации.

## 1. Жизненные ситуации (ЖС)

Система запускается с тремя ЖС:
1. Ветераны боевых действий.
2. Люди с инвалидностью.
3. Участники СВО и члены их семей.

**Требование к расширяемости**: перечень ЖС не фиксирован. Добавление новой ЖС
(и нового региона) должно выполняться через справочник (данные), **без
изменения кода**.

## 2. Роли

| Участник | Функция |
|---|---|
| Парсер | Ежедневно в 06:00 обходит источники, находит публикации, формирует сигналы |
| Бот | Интерфейс эксперта: сводки, карточки сигналов, приём ссылок |
| Эксперт | Изучает сигналы, отбирает релевантные, отправляет ссылку на НПА |
| Агент автообновления | Принимает ссылку на НПА, извлекает меры и параметры, возвращает структуру |

Агент автообновления — **уже существующий внешний сервис**, не часть этого
проекта. Контракт (API/webhook, формат запроса/ответа) на момент написания
неизвестен. Передачу ссылки от бота агенту нужно закладывать через
абстракцию/адаптер, чтобы позже подключить реальный контракт без переделки
ядра бота.

## 4. Ограничения для поиска

**4.1 По географии.** Парсер ищет публикации федерального уровня (действуют
на всей территории РФ) и регионального уровня (любой субъект РФ). Для каждого
сигнала система должна определить регион:
- по справочнику регионов РФ (89 субъектов);
- по источнику публикации (домен правительства региона);
- регион может уточняться по тексту публикации;
- если публикация федеральная — регион не указывается или указывается «РФ»;
- если регион не удалось определить — сигнал помечается «регион не
  определён» и получает **средний приоритет**.

**4.2 По типу документа.** Релевантны публикации, прямо или косвенно
указывающие на: федеральный закон; указ Президента РФ; постановление
Правительства РФ; приказ федерального министерства; закон субъекта РФ; указ
или постановление главы региона; постановление правительства региона; приказ
регионального министерства/департамента. Публикации без привязки к НПА —
нерелевантны.

**4.3 По типу события.** Парсер ищет публикации о: принятии нового документа;
внесении изменений в действующий; отмене или утрате силы; вступлении в силу
ранее принятого документа; изменении параметров мер (размер, сроки, условия,
порядок). Общие аналитические обзоры без указания на конкретный документ —
сигналы с **низким приоритетом**.

**4.4 По тематике.** Публикация релевантна, если одновременно: содержит
ключевые слова одной из ЖС **и** содержит слова из тематического блока мер
поддержки (см. раздел 5).

**4.5 По дате.** Обрабатываются публикации за последние 24 часа при
ежедневном запуске; за последние 7 календарных дней при первом запуске.

**4.6 По типу контента.** Только текстовые публикации: новости, анонсы,
карточки документов. Видео, подкасты, инфографика без текстового описания —
не обрабатываются.

## 5. Фильтрация по ключевым словам

**5.1 По ЖС:**
- Ветераны боевых действий: «ветеран боевых действий», «ВБД», «ветеран СВО»
- Люди с инвалидностью: «инвалид», «ребёнок-инвалид», «лицо с ограниченными
  возможностями», «инвалид с детства», «инвалид по зрению»
- Участники СВО: «участник СВО», «мобилизованный», «контрактник»,
  «доброволец», «члены семей участников СВО», «дети участников СВО»

**5.2 Тематический блок мер поддержки:** «мера поддержки», «выплата»,
«льгота», «пособие», «компенсация», «субсидии»

**5.3 Маркеры документа:**
- «постановление», «указ», «закон», «приказ», «распоряжение»
- «принят», «утверждён», «подписан», «вступил в силу», «внесены изменения»

**Решение по реализации:** классификация релевантности — гибрид. Жёсткие
правила по ключевым словам/regex из этого раздела — быстрый детерминированный
фильтр (первый проход). Поверх него — LLM (провайдер **GLM**; пример
использования и креды пользователь предоставит отдельно) для более гибких
задач: определение типа события, приоритета, извлечение названия/реквизитов
документа из текста публикации.

## 6. Модель сигнала

Для каждой релевантной публикации создаётся сигнал с полями:
- ID
- категория (одна или несколько ЖС)
- тип события: новый документ / изменение / отмена / вступление в силу / обзор
- приоритет: высокий / средний / низкий
- название документа (если извлечено)
- реквизиты (если извлечены)
- регион действия: «РФ» / конкретный субъект РФ / «Не определён»
- ссылка на публикацию
- дата и время создания
- статус: новый / в работе / отложен / отклонён / передан агенту

### Статусная модель

| Статус | Кто присваивает | Когда | Что означает | Где видит эксперт | Доступные действия | Куда переходит |
|---|---|---|---|---|---|---|
| Новый | Парсер | При обнаружении релевантной публикации | Сигнал создан, ещё не обработан | Утренняя сводка, `/today` | ✅ Взять в работу / ❌ Отклонить / ↩️ Позже | В работе / Отклонён / Отложен |
| В работе | Эксперт | При нажатии ✅ Взять в работу | Эксперт изучает, должен прислать ссылку на НПА | `/pending` | Прислать ссылку на НПА / ❌ Отклонить | Передан агенту / Отклонён |
| Отложен | Эксперт | При нажатии ↩️ Позже | Сигнал отложен, не потерян | `/pending` и следующая утренняя сводка | ✅ Взять в работу / ❌ Отклонить | В работе / Отклонён |
| Отклонён | Эксперт | При ❌ Отклонить + причина | Признан нерелевантным | `/history` | — | конечный статус |
| Передан агенту | Бот | После успешной проверки ссылки на НПА | Ссылка передана агенту извлечения, работа эксперта завершена | `/history` | — | конечный статус |

### Переходы

| Из | В | Действие | Кто выполняет |
|---|---|---|---|
| Новый | В работе | ✅ Взять в работу | Эксперт |
| Новый | Отклонён | ❌ Отклонить + причина | Эксперт |
| Новый | Отложен | ↩️ Позже | Эксперт |
| В работе | Передан агенту | Отправка корректной ссылки на НПА | Бот автоматически |
| В работе | Отклонён | ❌ Отклонить | Эксперт |
| Отложен | В работе | ✅ Взять в работу | Эксперт |
| Отложен | Отклонён | ❌ Отклонить | Эксперт |

### Приоритизация

- **Высокий** — прямое указание на ЖС + слова «новый», «изменение», «отмена»,
  «утратил силу», «индексация», «повышение» + есть ссылка на документ.
- **Средний** — косвенная связь с ЖС, нет ссылки на полный текст, или регион
  не определён.
- **Низкий** — аналитика, обзор, интервью без указания на конкретный
  документ.

## 7. Работа бота (Telegram)

Подтверждено с пользователем: интерфейс эксперта реализуется как
**Telegram-бот** (inline-кнопки ✅❌↩️, команды со слэшем).

**Утренняя сводка** — пример:
```
Утренняя сводка — 18.08.2026
Найдено сигналов: 5
Высокий приоритет: 2 | Средний приоритет: 2 | Низкий приоритет: 1

1. Москва | Указ Мэра о новой выплате участникам СВО
   Источник: mos.ru
   /signal_1
...
```

**Карточка сигнала** — категория, регион, тип события, приоритет, название,
реквизиты, источник, ссылка на публикацию, действия (✅/❌/↩️).

**Действия с сигналом:**
- ✅ Взять в работу → статус «В работе», бот запрашивает ссылку на полный
  текст НПА (поддерживаются HTML-страницы).
- ❌ Отклонить → бот запрашивает причину: [Не относится к целевым категориям]
  / [Дубликат] / [Не является НПА] / [Другое]. Статус «Отклонён», сигнал
  больше не показывается.
- ↩️ Позже → сигнал остаётся, бот напомнит в следующей сводке.

**Приём ссылки на НПА:** бот проверяет доступность страницы. Если
недоступна — просит проверить/прислать снова или загрузить файл напрямую.
Если корректно — «✅ Ссылка принята», статус → «Передан агенту».

**Команды:**
- `/today` — Новый, Отложен за сегодня
- `/pending` — В работе, Отложен
- `/history` — Передан агенту, Отклонён — последние 10
- `/stats` — все статусы, агрегированная статистика за неделю

## 8. Happy path

1. В 06:00 парсер обходит источники.
2. В 08:00 бот присылает эксперту сводку.
3. Эксперт открывает сигнал, нажимает ✅ Взять в работу.
4. Бот просит ссылку на НПА.
5. Эксперт отправляет ссылку.
6. Бот проверяет ссылку и передаёт агенту автообновления.

## 9. Граничные случаи

**Парсинг:**
- Источник недоступен — 3 попытки, затем пропуск до следующего цикла.
- Нет новых публикаций — бот отправляет «Новых сигналов нет».
- Публикация уже обработана — дубликат не создаётся.

**Ссылка на НПА:**
- Ссылка недоступна — бот просит проверить.

**Эксперт:**
- Сигнал более 3 дней в «В работе» — бот присылает напоминание.
- Эксперт отклонил сигнал — сигнал помечается и не возвращается.
- Эксперт нажал «Позже» — сигнал появится в следующей сводке.

## 10. Безопасность

- Бот работает только с ID допущенных пользователей.
- Сообщения от посторонних игнорируются.
- Все действия логируются.
- Передаваемые ссылки проверяются на допустимые домены (белый список).

## 11. Критерии готовности

Система готова, если:
- парсер ежедневно в 09:00 обходит федеральные, региональные и сигнальные
  источники (в разделе 8 ТЗ фигурирует 06:00 для сбора и 08:00 для сводки —
  09:00 в критериях готовности как в оригинале ТЗ; уточнить фактическое время
  при реализации);
- бот присылает сводку;
- эксперт может взять сигнал в работу, отклонить или отложить;
- бот принимает и проверяет ссылку на НПА;
- бот передаёт ссылку агенту;
- добавление новой ЖС и нового региона выполняется через справочник без
  изменения кода;
- работают команды `/today`, `/pending`, `/history`, `/stats`;
- обрабатываются все описанные граничные случаи.

## 12. Архитектурные решения

Зафиксированы с пользователем при постановке задачи (2026-08-19):

- **Бот-платформа**: Telegram.
- **Язык/стек**: Python (парсинг HTML/RSS — requests/bs4/feedparser; бот —
  aiogram или аналог; cron-джобы; работа с Excel и LLM API).
- **Хранилище**: SQLite — сигналы, история статусов, справочники ЖС и
  регионов.
- **Деплой**: свой сервер/VPS, Docker (крон парсера, бот, БД). Детали
  инфраструктуры не финализированы.
- **Классификация**: гибрид regex-правил (раздел 5 этого файла) + LLM (GLM)
  для типа события/приоритета/реквизитов. Провайдер и креды — TBD, см. раздел
  13.
- **Агент автообновления**: внешний, уже существует. Контракт API неизвестен
  → реализовывать через адаптер/интерфейс внутри бота, чтобы подключение
  реального API не требовало переделки ядра.
- **Справочник регионов/источников**: строится из `pravo.gov.ru/links/region/`
  как отправной точки; парсер работает по белому списку доменов; справочник —
  часть данных проекта, редактируется без изменения кода (как и справочник
  ЖС).

## 13. Целевая схема данных меры (из `Для проверки обновления.xlsx`)

Файл `docs/Для проверки обновления.xlsx` — не входные требования, а пример
**выходных данных**, которые после извлечения агентом автообновления описывают
меру поддержки. Полезно как ориентир формата, к которому в итоге приводится
цепочка сигнал → НПА → извлечённая мера. Листы: `Инвалиды 2025/2026`,
`ВБД 2025/2026`, `СВО 2025/2026`.

Общие поля по ЖС (с вариациями по листам):
- `measureId` — идентификатор меры (например `77_1`, `00_vbd_29`,
  `77_svo_16`); префикс `00_` = федеральная мера, `77_` = региональная
  (Москва в примерах);
- `region` — регион действия («РФ» или название субъекта);
- признаки категории получателя — по ЖС разные наборы столбцов:
  - Инвалиды: `cause_general_disease`, `cause_war_trauma`, `cause_radiation`,
    `cause_disabled_child` (флаги 0/1) + суммы по группам инвалидности
    (`measure_first_group` … `measure_disabled_child`);
  - ВБД: `СategoryOfVeteran` (категория получателя текстом, напр.
    «Военнослужащие», «Обслуживающие воинские части», «Работники в зоне
    боевых действий»);
  - СВО: `categoryMobilized`, `categoryContractor`, `categoryVolunteer`,
    `kidsOfMilitary` (флаги 0/1);
- `measureName` — название меры;
- `measureSum` / суммы по группам — размер выплаты (может быть текстом,
  напр. «до 114 000 ₽», «индивидуально»);
- `measurePeriodicity` — периодичность (единовременно/ежемесячно/ежегодно);
- `measureTerms` — условия получения (свободный текст);
- `department` — куда обращаться / кто оформляет;
- `measureType` — тип меры (выплата/льгота/...);
- `measureLevel` — уровень (региональные/федеральные);
- `Ссылка на источник` — где эксперт/агент нашёл описание меры;
- `Ссылка на НПА` (и `Ссылка на НПА1/2`, `Пункт НПА1/2`) — нормативная база,
  возможна привязка к нескольким НПА и конкретным пунктам;
- доп. поля, появившиеся в версии 2026: `Категория льготы`,
  `Кнопка Оформить (ссылка)`, `Контакты`, `Признак индексации` — то есть
  формат со временем расширяется (ещё один аргумент за схемой, допускающей
  рост полей без миграции кода).

Это подтверждает, что сравнение версий по годам (2025 vs 2026 для одного и
того же `measureId`) — способ увидеть, что именно меняет НПА (сумма выплаты,
условия, появление новых полей вроде индексации).
