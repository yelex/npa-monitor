# Спека: ретроактивная чистка уже накопленных сигналов на проде (PLAN.md Фаза 9, п.7)

Статус: **реализовано, 2026-08-24**.

## 1. Проблема

Все пункты Фазы 9 (п.1–п.3, п.5, п.6) чинят код парсера так, чтобы **новые** обходы
источников не создавали проблемные сигналы (многолетние публикации, дубликаты,
заниженный приоритет, ложные срабатывания классификатора). Ни один из них не трогает
сигналы, уже накопленные на боевом VPS до этих фиксов (105 сигналов дампа
2026-08-20…24 плюс всё, что накопилось после дампа до деплоя текущей версии).

Вопрос пользователя: можно ли применить те же фиксы **задним числом** к уже
существующей боевой БД — то есть почистить накопленные сигналы в соответствии с
логикой последних 6 коммитов, а не только защитить будущее.

## 2. Что применимо ретроактивно, а что нет

`Signal` (`db/models.py`) хранит только `title` + `source_url`, не полный текст
публикации. Живой классификатор (`parser/classifier.py::_publication_text`) работает
на `title + summary` из листинга источника — `summary` при создании сигнала никогда не
сохранялся (`parser/signals.py::build_signal` копирует только `title`). Это делит
задачу на две группы по достижимой точности:

**Можно сделать точно, без сети и без потери информации** (данные уже есть в БД):
- Исключение по URL-паттерну (п.1/п.3, `parser/filters.py::is_excluded_path`) —
  работает на `source_url`, ничего не теряется.
- Дедуп по каноническому URL (п.2 часть 1, `parser/dedup.py::canonicalize_url`) —
  тоже работает на `source_url`.
- Дедуп по содержанию заголовка (п.2 часть 2, `parser/dedup.py::find_duplicate_title`)
  — работает на `title`, который есть.

**Можно сделать только приближённо** (нет `summary`, признак задокументирован как
ограничение, не как баг):
- Пересчёт приоритета (п.5, `detect_priority`) — исходно считался на `title + summary`,
  пересчитывается на одном `title`. Не меняет уже стабильный факт «дальше высокий текст
  не тянет вниз» — приоритет может только вырасти относительно исходного (стемминг
  «новый»/«инвалид» и т.п. фиксы всегда расширяют совпадения, не сужают), риск
  ложного занижения при пересчёте отсутствует, риск ложного **завышения** —
  теоретический (если весь смысл держался на `summary`, которого нет) и не критичен:
  приоритет не блокирует ни один переход статуса (раздел 6 AGENTS.md), только сортировку
  сводки.
- Аудит на ложные срабатывания (п.6, релевантность) — та же нехватка `summary`, но
  здесь ошибка **опаснее**: если `title` в одиночку не даёт того же результата, что
  давал `title + summary`, авто-снятие релевантного сигнала как «ложного срабатывания»
  может выкинуть реальную публикацию. **Решение: только отчёт, без авто-применения**
  (раздел 4, шаг D) — see раздел 5.

Альтернатива с более высокой точностью — перескачать текст публикации заново по
`source_url` для каждого сигнала и прогнать классификатор на свежем тексте. Сознательно
не выбрана как обязательный путь: часть URL в дампе уже невоспроживодима (см.
`docs/SPEC_classifier_false_positives.md`, раздел 2 — 401/CAPTCHA/нет в Wayback Machine
уже для публикаций недельной давности), а часть требует RU-прокси (RSNET), которого
может не быть в момент разового прогона чистки. Обязательный к сети путь означал бы
«чистка невозможна для части сигналов» вместо «чистка возможна везде с задокументированной
точностью» — второе выбрано как более полезное по умолчанию.

## 3. Область применения — какие сигналы трогать

Только `Signal.status in (NEW, POSTPONED)` («Новый», «Отложен») — это единственные
статусы, где эксперт ещё не принял решение (раздел 6 AGENTS.md). Никогда не трогаются:
`IN_PROGRESS` (эксперт уже работает), `SENT_TO_AGENT`/`COMPLETED` (уже ушло вовне/
завершено), `REJECTED` (решение эксперта, финальное — раздел 6 AGENTS.md: «конечный
статус»; повторное открытие — осознанное ручное действие `/reopen`, не массовая чистка).

## 4. Решение — `scripts/cleanup_signals.py`

Одноразовый CLI-скрипт (не часть боевого пайплайна, не крон), запускается вручную на
той же машине, где лежит `npa_monitor.db` (по аналогии с `scripts/dump_signals.py`).

**Режим по умолчанию — отчёт (dry-run), без записи в БД.** `--apply` применяет шаги
A/B/C. Шаг D **никогда** не применяется автоматически — только текст отчёта, независимо
от `--apply` (раздел 2 — риск ложного снятия релевантного сигнала).

- **Шаг A — URL-исключения (п.1/п.3).** Для каждого активного сигнала —
  `is_excluded_path(signal.source_url)`. Совпадение → `transition_status(...,
  SignalStatus.REJECTED, rejection_reason=RejectionReason.NOT_NPA, changed_by=
  "cleanup_script", reason="Фаза 9 п.1/п.3: статичная справочная страница, ретроактивная чистка")`.
- **Шаг B — дедуп.**
  - B1 (URL): группировка активных сигналов по `canonicalize_url(source_url)`.
    Внутри группы >1 — оставить сигнал с минимальным `id` (= раньше создан), остальные
    → `REJECTED`/`DUPLICATE`, `reason` со ссылкой на id оставленного.
  - B2 (заголовок): среди оставшихся после B1, отсортированных по `created_at`,
    для каждого следующего сигнала — `find_duplicate_title` по всем более ранним
    активным сигналам в пределах `TITLE_DEDUP_WINDOW` (5 дней), `llm_client=
    get_default_client()` (тот же порядок деградации, что в бою — без GLM в `.env`
    просто не ловит пограничные случаи, точное совпадение заголовка ловится всегда).
    Совпадение → `REJECTED`/`DUPLICATE`.
- **Шаг C — пересчёт приоритета (п.5).** Для оставшихся активных сигналов —
  `detect_priority(signal.title or "", keywords, signal.region)` (регион берётся уже
  сохранённый, не пересчитывается — не менялась логика `detect_region`). Отличается от
  текущего `signal.priority` → обновить поле напрямую (это не переход статуса, в
  `StatusHistory` не пишется — таблица только про статус, раздел 7 AGENTS.md не
  описывает приоритет как часть аудита переходов).
- **Шаг D — аудит релевантности (п.6, только отчёт).** Для оставшихся активных сигналов
  — `classifier.explain(Publication(title=signal.title, url=signal.source_url,
  published_at=signal.created_at, source_key=...))` (без `summary`). Если
  `is_relevant is False` — печатается как кандидат на ручную проверку с трейсом
  (`trace.format()`), **без изменения статуса**. Дальнейшее решение — эксперт/пользователь
  вручную (существующий `/reopen`+`❌ Отклонить` через бота, эта задача не добавляет
  новый механизм массового отклонения для шага D намеренно).

### Порядок и идемпотентность

A → B1 → B2 → C → D, каждый следующий шаг видит уже отклонённые предыдущим шагом
сигналы как неактивные (не участвуют дальше). Повторный запуск с `--apply` на уже
почищенной БД безопасен: A/B на `REJECTED`-сигналах больше не сработают (не входят в
область применения, раздел 3), C увидит те же активные сигналы и посчитает тот же
приоритет (не изменится второй раз), D напечатает тот же (уже меньший) список кандидатов.

### Не покрыто этим скриптом

- Одноразовая ALTER-миграция `DocumentSeen.title` (`db/session.py::_ensure_columns`,
  Фаза 9 п.2 часть 2) — применяется автоматически при следующем запуске
  бота/парсера/этого скрипта через `init_db()`, отдельного шага не требует.
- Обзоры без НПА (Фаза 9 п.4) — заблокировано продуктовым решением, вне периметра.

## 5. Почему шаг D — только отчёт

Пользователь при выборе объёма задачи (AskUserQuestion, 2026-08-24) сам определил этот
пункт как «самый рискованный, минимум false negative на реально релевантных». Плюс
структурная причина (раздел 2) — без `summary` пересчёт релевантности по одному
заголовку менее надёжен, чем исходная классификация. Авто-отклонение здесь было бы
попыткой всё-таки закрыть п.6 массово, тогда как даже в самой Фазе 9 п.6
(`docs/SPEC_classifier_false_positives.md`) точная причина ложных срабатываний [33]/[34]
осталась неподтверждённой и была закрыта через синтетический аудит справочника, а не
через прогон на реальных данных.

## 7. Открытые вопросы

- Запуск на боевом VPS — из этой сессии нет SSH-доступа (AGENTS.md раздел 16, п.11:
  актуальность доступа не подтверждена). Скрипт разрабатывается и тестируется локально
  (in-memory/tmp sqlite, `tests/test_cleanup_signals.py`); реальный прогон на
  `npa_monitor.db` пилота — отдельное ручное действие пользователя (или отдельный запрос
  с явным подтверждением), **обязательно с бэкапом файла БД перед `--apply`**.
  `data/` внутри контейнеров смонтирован как именованный docker-том `npa_data`
  (`docker-compose.yml`), не bind-mount хостового пути — значит `cp` на самом хосте
  (`/opt/npa-monitor/data/...`) файл не найдёт, копировать нужно **внутри контейнера**:
  `ssh ... "cd /opt/npa-monitor && docker compose exec -T bot cp data/npa_monitor.db
  data/npa_monitor.db.bak-$(date +%F)"` (тот же приём «бэкап = cp файла», PLAN.md
  раздел 2, применён к правильному месту хранения).

## 8. Дополнение — сверка с уже отклонёнными вручную сигналами

Реальный прогон `scripts/cleanup_signals.sh` на боевой БД (2026-08-24) нашёл 0
активных сигналов: из 105 сигналов дампа пилота эксперт к этому моменту уже вручную
разобрал всё — 91 «Отклонён», 10 «В работе», 4 «Передан агенту» (раздел 3 — область
применения скрипта пуста). Область применения `cleanup_signals.py` (раздел 3) —
намеренно только `NEW`/`POSTPONED`, поэтому чистка не может дотянуться до уже
отклонённых сигналов, и это ожидаемо, не баг.

Чтобы всё же проверить, действительно ли фиксы Фазы 9 закрывают то же самое, что
эксперт чистил руками — `scripts/audit_rejected_signals.py`: read-only сверка,
прогоняет ту же детекцию (шаги A/B1/B2/D, без C — приоритет не про причину отклонения)
по уже отклонённым сигналам и сравнивает с их `rejection_reason`. Никогда не пишет в
БД (не вызывает `init_db()`, нет `--apply`) — отдельный от `cleanup_signals.py`
самодостаточный файл (та же причина, что и у `dump_signals.py`: скармливается в
контейнер через stdin, не должен зависеть от того, задеплоен ли сам файл на сервере).
