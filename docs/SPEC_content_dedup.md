# Спека: вторичный слой дедупа по содержанию (заголовок + LLM), PLAN.md Фаза 9 п.2

Статус: **реализовано, 2026-08-24** (PLAN.md Фаза 9, п.2, 2-й и 3-й под-пункты — из
[SPEC_url_canonicalization.md](SPEC_url_canonicalization.md) уже закрыт 1-й).

## 1. Проблема

Канонизация URL (`parser/dedup.py::canonicalize_url`, предыдущая итерация) не схлопывает
дубликаты, у которых разные и домен/поддомен, и путь — только разница в схеме/`www.`/
шумовых query-параметрах одного и того же URL-паттерна. Из живого дампа
(`signals_dump.txt`, AGENTS.md раздел 16 п.15) остаются:

1. **Синдикация `*.mos.ru` по районным поддоменам** — одна и та же новость («Ветераны
   боевых действий столичного региона смогут быстрее…») публикуется на нескольких
   районных поддоменах mos.ru с идентичным или почти идентичным заголовком, но разными
   путями и разными числовыми ID документа (сигналы [100]/[86]/[61]/[40] — заголовок в
   дампе дословно совпадает; отдельно проверено этой сессией, что [56] в исходной пометке
   в PLAN.md — на самом деле другая статья, «Какие налоговые льготы…», с другим
   заголовком, то есть не дубликат, см. раздел 6 «отклонения от плана»).
2. **Зеркала одного документа на разных доменах** — `minjust.consultant.ru/documents/60711`
   vs `.../special/documents/document/60711` (сигналы [49]/[24]) — тот же документ, разные
   пути на одном домене (задокументированное ограничение канонизации URL, см.
   `SPEC_url_canonicalization.md`, раздел 3).

Общее свойство: у листинговых адаптеров (`parser/sources/*`) есть только заголовок,
ссылка и дата публикации — не полный текст статьи (`parser/orchestrator.py`, докстринг:
«адаптеры дают только заголовок/ссылку/дату из листинга, не скачивая каждую статью»).
Значит, сравнение «тот же документ по сути» может опираться **только на заголовок**
(плюс `summary`, если источник его отдаёт) — без дополнительного сетевого запроса на
каждую публикацию (что и обсуждалось как нежелательное архитектурное расширение в
`docs/SPEC_stale_publications_filter.md`, раздел 4, для похожей по духу задачи).

## 2. Решение пользователя (2026-08-24, зафиксировано в AGENTS.md раздел 5 и PLAN.md
Фаза 9 п.2)

LLM (GLM, `parser/llm.py::ClassifierLLMClient`/`GLMClient`) закладывается как **основной**
инструмент сравнения «та же публикация по сути», не только точечный fallback узких мест
— нормализация заголовка (regex/строковая близость) плохо справляется с перефразированными
заголовками одной новости. Обязательное условие сохраняется: деградация до обычной
нормализации, если `parser.llm.get_default_client()` вернёт `None` (GLM не сконфигурирован)
— LLM не становится обязательным звеном пайплайна.

**Важное уточнение по факту дампа:** в примерах [100]/[86]/[61]/[40] заголовок совпадает
**дословно** — точная нормализация уже их поймала бы без LLM. LLM в этой задаче closes
именно паре случаев, где заголовок переформулирован по-разному (общий класс риска,
подтверждённого пока не в этом дампе, но явно предвидимого — синдикация с разных
редакций/CMS обычно меняет заголовок). Реализация поэтому — двухступенчатая: точное
совпадение нормализованного заголовка сначала (дёшево, без сети), LLM — только для
кандидатов, которые *похожи, но не совпадают дословно* (иначе на каждую новую публикацию
уходил бы LLM-запрос впустую).

## 3. Архитектура

### 3.1 Хранение

`db.models.DocumentSeen` получает новое поле `title: str | None` (Text, nullable) —
заголовок публикации на момент первого обнаружения, нужен только как материал для
сравнения, не показывается эксперту.

**Эксплуатационное следствие:** в проекте нет Alembic (`db/session.py`, раздел 2 PLAN.md
— «миграции появятся на следующем этапе»), `init_db`/`create_all` не добавляет колонки в
уже существующую таблицу. На боевом VPS уже накоплена продовая `documents_seen` (пилот
идёт с 2026-08-20). Без миграции `register_document_seen` упадёт на первой же записи
после деплоя этой задачи (`no such column: title`). **Решение:** добавить в `db/session.py`
маленькую идемпотентную функцию `_ensure_column` (PRAGMA `table_info` → `ALTER TABLE …
ADD COLUMN` при отсутствии), вызываемую из `init_db` до `create_all` — точечный обход
отсутствия Alembic для этого конкретного случая, не замена миграций в целом (нужно
явно задокументировать как временную меру, см. раздел 7).

### 3.2 Сравнение

Новые функции в `parser/dedup.py`:

- `normalize_title(title: str) -> str` — токенизация по `[а-яёa-z0-9]+` (без учёта
  регистра), склейка через пробел. Не лемматизация (`parser/ru_stem.py` — обрезка
  окончаний под конкретный класс задач классификации, здесь не нужна: сравниваем строки
  целиком, не отдельные ключевые слова).
- `title_similarity(a: str, b: str) -> float` — коэффициент Жаккара по множествам
  нормализованных токенов — дешёвая предварительная оценка «похожести», чтобы не звать
  LLM на заведомо разные заголовки.
- `find_duplicate_title(candidate_title, existing, *, llm_client=None) -> int | None` —
  `existing` — `Iterable[tuple[id, title, signal_id]]` (недавно виденные документы, окно
  ниже). Точное совпадение нормализованного заголовка → сразу возвращает `id` (без LLM).
  Иначе — берёт кандидата с максимальным `title_similarity` в «пограничной» зоне
  (`TITLE_CANDIDATE_MIN_SIMILARITY <= score < 1.0`) и, если `llm_client` задан, просит LLM
  подтвердить/опровергнуть одним словом (да/нет). Ошибка LLM (`LLMError`) — не поднимается
  наружу, трактуется как «нет» (деградация, не сбой всего прогона).

### 3.3 Окно сравнения

Сравнивать нужно не со всей историей `documents_seen` (дороже и бессмысленно — публикация
месячной давности не может быть дубликатом сегодняшней), а с недавними записями.
`TITLE_DEDUP_WINDOW = 5 дней` — с запасом относительно наблюдённого в дампе разрыва
(1–3 дня между дублирующими сигналами на разных поддоменах mos.ru). Источник кандидатов —
`db.service.recent_documents_with_titles(session, *, since, exclude_id)`.

### 3.4 Точка подключения

`parser/orchestrator.py::_process_publication`, **после** дедупа по URL (раздел уже
реализован, `canonicalize_url`), но **только если URL оказался новым** — если URL уже
дублирует что-то в `documents_seen`, повторный контент-дедуп не нужен (та же ссылка уже
разобрана раньше). Ключевое следствие: LLM-сравнение выполняется не на каждый повторный
обход, а **не более одного раза на новый URL** — стоимость LLM-вызовов растёт вместе с
числом новых публикаций, а не с числом прогонов парсера.

При найденном дубле — не создаём сигнал (`result.duplicates += 1`), но запись
`documents_seen` для нового URL всё равно остаётся (со своим `title`, `signal_id` =
`signal_id` найденного дубля, если он есть, иначе `None`) — чтобы этот URL при повторном
обходе уже ловился первым (URL-based) слоем дедупа без повторного LLM-сравнения.

`run_all`/`process_source` получают новый опциональный параметр `llm_client:
ClassifierLLMClient | None = None`; `run_all` по умолчанию берёт
`parser.llm.get_default_client()`, если явно не передан (тот же паттерн, что уже
использует `Classifier.load()` для справочников — ленивая инициализация по умолчанию,
переопределяемая в тестах).

## 4. Что не делает эта задача

- Не сравнивает полный текст документов (только заголовок/`summary` из листинга) — по
  причине раздела 1 (нет сетевого запроса на каждую публикацию).
- Не решает Фазу 9 п.3 («не пересоздавать сигнал по URL, отклонённому экспертом ранее»)
  — тот пункт про решение эксперта (`rejected`), не про факт «уже видели контент»; он
  зависит от этой задачи (переиспользует `canonicalize_url`), но реализуется отдельно.
- Не переносит существующие записи `documents_seen` без `title` (накопленные до этой
  задачи) — у них `title IS NULL`, они просто не участвуют как кандидаты в
  `recent_documents_with_titles` (WHERE title IS NOT NULL) и не сравниваются задним числом.

## 5. Открытые вопросы, требующие решения перед стартом

Нет — оба содержательных решения (роль LLM, отказ от дедупа по полному тексту) уже
зафиксированы пользователем (раздел 2) и архитектурой оркестратора (раздел 1). Единственная
находка этой спеки, требующая явного технического решения — раздел 3.1
(`_ensure_column`) — решение принято тут же (точечный ad hoc migration hook, не полноценный
Alembic), задокументировать риск в PLAN.md «Открытые внешние зависимости» (боевая БД
требует ручной проверки после деплоя — `_ensure_column` идемпотентна и должна отработать
автоматически при следующем старте бота/парсера на VPS, но стоит перепровери).

## 6. Результат выполнения

Реализовано ровно по разделу 3, без отклонений от плана.

- **`db/models.py`** — `DocumentSeen.title: str | None`.
- **`db/session.py`** — `_ensure_columns()`/`_COLUMNS_ADDED_AFTER_INITIAL_SCHEMA`,
  вызывается из `init_db` перед `create_all` (PRAGMA `table_info` → `ALTER TABLE … ADD
  COLUMN`, идемпотентно). Проверено тестом на «легаси»-схеме без Alembic (см. ниже).
- **`db/service.py`** — `register_document_seen` принимает `title`;
  `recent_documents_with_titles(session, *, since, exclude_id)` — кандидаты для
  сравнения (только с `title IS NOT NULL`, в пределах окна);
  `link_document_to_signal(session, document, *, signal_id)`.
- **`parser/dedup.py`** — `normalize_title`, `title_similarity` (Жаккар по токенам),
  `TITLE_CANDIDATE_MIN_SIMILARITY = 0.4`, `TITLE_DEDUP_WINDOW = 5 дней`,
  `find_duplicate_title(candidate_title, existing, *, llm_client=None)` — точное
  совпадение сразу, иначе пограничная зона решается LLM (промпт
  `_SAME_PUBLICATION_PROMPT`), `LLMError` внутри трактуется как «нет».
- **`parser/orchestrator.py`**:
  - `_process_publication` — после URL-дедупа (создан новый `DocumentSeen` с `title`)
    вызывает `find_duplicate_title` по кандидатам за окно; при совпадении —
    `result.duplicates += 1`, сигнал не создаётся, документ линкуется на найденный
    `signal_id` через `link_document_to_signal`, сигнал заново не создаётся.
  - **Побочная находка и фикс, не входившая в исходный план раздела 3:**
    `documents_seen.signal_id` вообще нигде не проставлялся при создании *первого*
    сигнала по публикации (ни до этой задачи, ни в черновике этой) — цепочка привязки
    дублей молчаливо вырождалась в `signal_id=None` уже на первом шаге. Добавлен вызов
    `link_document_to_signal(session, document, signal_id=signal.id)` сразу после
    `build_signal` в `_process_publication`.
  - `process_source`/`run_all` — новый параметр `llm_client: ClassifierLLMClient | None`.
    `run_all` использует служебный sentinel `_UNSET`, чтобы отличить «не передан»
    (берётся `parser.llm.get_default_client()`) от явного `None` (тесты).
    `parser/__main__.py` не менялся — вызывает `run_all` без `llm_client`, значит с
    выходом в прод автоматически подключит GLM, если `.env` его содержит (раздел 2 —
    первое реальное включение `parser/llm.py` в боевой путь, до этого модуль был
    написан, но нигде не вызывался).

## 7. Открытые вопросы после реализации

1. 🟡 **Эксплуатационный риск для боевой БД** (раздел 3.1) — `_ensure_columns` не
   проверена на реальном файле `.db` пилота (нет доступа к VPS). Логика идемпотентна и
   покрыта тестом на синтетической «легаси»-таблице, но перед реальным деплоем стоит
   сделать `cp` бэкап боевого `npa_monitor.db` (как и раньше — «бэкап = `cp` файла»,
   PLAN.md раздел 2) до первого перезапуска с этой версией кода.
2. 🟢 Роль LLM для этого сравнения — решение пользователя от 2026-08-24 реализовано
   буквально (раздел 2), деградация подтверждена тестом.
3. 🟡 `TITLE_CANDIDATE_MIN_SIMILARITY = 0.4` и `TITLE_DEDUP_WINDOW = 5 дней` — начальные
   константы по эвристике из раздела 3, не откалиброваны на большом наборе живых
   примеров (в дампе — только один content-дубль-кейс с дословным совпадением). Если
   пилот покажет ложные срабатывания (два разных события с похожими заголовками) или
   пропуски (переформулировка сильнее 0.4-порога) — пересмотреть по факту новых
   примеров, не заранее.
4. 🔴 Фаза 9 п.3 («не пересоздавать сигнал по отклонённому URL») по-прежнему не начата
   — зависит от `canonicalize_url` (готово), может дополнительно опереться на
   `find_duplicate_title` тем же образом, но это отдельная задача.
