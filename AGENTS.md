# AGENTS.md — Мониторинг изменений в НПА (меры поддержки)

> Постоянный контекст проекта. Часть более крупной инициативы «Агент автообновления» —
> здесь описан только контур **обнаружения и сигнализации об изменениях в НПА**, а не сам
> экстрактор карточек мер.
>
> Этот файл объединяет две линии работы над одним проектом: локальный разбор исходного
> ТЗ (`docs/Требования_к_мониторингу_изменений_в_НПА.html`,
> `docs/Для проверки обновления.xlsx`) и более позднюю, уточнённую с заказчиком версию
> из репозитория [`yelex/npa-monitor`](https://github.com/yelex/npa-monitor) (см. `git remote -v`,
> `origin`). Там, где версии расходятся, ниже зафиксирован актуальный, уточнённый вариант,
> а расхождение явно помечено — история решений важнее видимости единого черновика.

---

## 1. Цель

Автоматизировать ежедневный мониторинг публикаций о принятии, изменении или отмене
нормативных документов по трём жизненным ситуациям (ЖС) и обеспечить передачу
релевантных НПА эксперту (аналитику) на изменение данных после ручного подтверждения.

**ЖС в скоупе:**
1. Ветераны боевых действий (ВБД)
2. Люди с инвалидностью
3. Участники СВО и члены их семей

**Требование к расширяемости**: перечень ЖС не фиксирован. Добавление новой ЖС (и нового
региона) должно выполняться через справочник (данные), **без изменения кода**.

**MVP-периметр (уточнено):** только Москва (77) + федеральный уровень, где применимо
(аналогично листам `Инвалиды 2025/2026`, `ВБД 2025/2026`, `СВО 2025/2026` в
`Для проверки обновления.xlsx`). Расширение на все 89 субъектов РФ — после пилота.
Справочник регионов при этом проектируется сразу расширяемым (см. раздел 4), просто
заполняется в MVP только Москвой + «РФ».

Источники требований:
- `docs/Требования_к_мониторингу_изменений_в_НПА.html` — полное исходное ТЗ.
- `docs/Для проверки обновления.xlsx` — примеры уже собранных мер поддержки (6 листов:
  Инвалиды/ВБД/СВО × 2025/2026) — целевая структура данных, которую производит внешний
  «агент автообновления».
- Файл `Методика_и_критерии_оценки_качества_извлечения_данных.docx` упоминается как
  источник в связанном репозитории (методика приёмки качества экстракции карточек,
  Recall/Precision/QS) — **отдельный контур**, к мониторингу изменений НПА относится
  только справочно (общий словарь полей карточки меры), в этом проекте не реализуется.
  Файла нет в `docs/` этого репозитория — при необходимости запросить у заказчика.

Это не совсем greenfield-проект: практическая часть (справочники, схема БД, разбор
источников, сетевая диагностика) уже частично сделана в `yelex/npa-monitor` — см.
`docs/STAGE0.md` и раздел 15 ниже. Код приложения (`parser/`, `bot/`, `db/`) пока не
написан ни там, ни здесь.

## 2. Роли

| Роль | Кто | Функция |
|---|---|---|
| Парсер | сервис (cron) | ежедневно обходит источники, находит публикации, формирует сигнал |
| Бот | Telegram-бот | интерфейс эксперта: карточки сигналов, команды, сводки |
| Эксперт (аналитик) | 1 человек | изучает сигнал, отбирает релевантные, отправляет ссылку на НПА агенту |
| Агент автообновления | LLM-агент, внешний по отношению к этому контуру | получает ссылку на НПА от эксперта, извлекает изменения, обновляет карточку меры; результат по этому сигналу возвращается эксперту на финальную проверку |

Агент автообновления — **уже существующий внешний сервис** (в измерениях этого
проекта), физически это локальный проект `/Users/user/dev/auto` (LangGraph-пайплайн
`product_agent`, Sberbank-инфраструктура). Стабильного вызываемого контракта (API/
webhook) пока нет — подробности и открытый выбор стратегии интеграции см. раздел 16,
пункт 8. Передачу ссылки от бота агенту нужно закладывать через абстракцию/адаптер,
чтобы позже подключить реальный контракт без переделки ядра бота.

Разграничение прав по регионам/категориям — не требуется в MVP (эксперт один).

## 3. Технологии

- Python + cron + Docker на VPS.
- Telegram Bot API (интерфейс эксперта: карточки, инлайн-кнопки `✅/❌/↩️`, команды).
- БД — SQLite (WAL-режим) через SQLAlchemy 2.0 + Alembic; переход на Postgres при
  расширении за пределы MVP — почти бесшовный благодаря ORM-слою.
- Бот — `aiogram` 3 (async, встроенный FSM для многошаговых сценариев: запрос ссылки на
  НПА, причины отклонения), long-running polling-процесс, не вебхук.
- Fetcher — `httpx` + `tenacity` (retry с бэкоффом).
- PDF — `PyMuPDF`/`pdfplumber` как основной слой (тексто-слойные PDF), `pytesseract`
  как OCR-fallback, если текстового слоя нет.
- За основу поиска мер частично переиспользуются отдельные приёмы (не архитектура и не
  код целиком) из `https://github.com/yelex/measure_deepagent` — разбор см. в
  `docs/STAGE0.md`, раздел 1.
- Отдельная БД для сигналов (очередь `/pending`, история `/history`), схема полей — по
  разделу 7 ниже. Плюс связь «сигнал → measureId» для меры, которую он затрагивает
  (заполняется/подтверждается экспертом вручную).

Полная разбивка на процессы (`parser/`, `bot/`, `db/`) и оценка по этапам — в
[PLAN.md](PLAN.md).

## 4. Источники и парсинг

**Белый список источников:**
- Федеральные: `publication.pravo.gov.ru`, `kremlin.ru`, `government.ru`, `sfr.gov.ru`,
  `mintrud.gov.ru`.
- Региональные (Москва в MVP): официальный портал правительства региона
  (`mos.ru/authority/documents/`), сайт регионального минтруда/соцзащиты
  (`msupport.dszn.ru`, `dszn.ru` — требует уточнения, см. `docs/STAGE0.md`), портал
  правовой информации региона (если есть — для Москвы отдельного домена не найдено,
  рабочая гипотеза: это и есть `mos.ru/authority/documents/`), официальный сайт главы
  региона.
  - Список ссылок по всем 89 регионам можно спарсить с
    `http://pravo.gov.ru/links/region/` — держать как справочник для будущего
    расширения за пределы Москвы. Справочник региона proектируется сразу расширяемым
    (регион → набор доменов-источников), даже если в MVP заполнен только Москвой.
- Иные (для контекста, не как единственное основание для сигнала без подтверждения):
  `garant.ru`, `consultant.ru`, `docs.cntd.ru/comments`, `tass.ru`, `ria.ru`, а также
  `rg.ru` («Российская газета» — официальный публикатор НПА, полезен как alternative
  источник конкретного акта, не как основной листинг для обхода).
  - `gosuslugi.ru` рассматривался, но не отвечает даже через прокси (см.
    `docs/STAGE0.md`) — в whitelist парсера не включён.

Актуальный статус проверки каждого источника (что отвечает, что требует прокси/JS-рендера)
— в `docs/STAGE0.md`, раздел 2.

**Задача парсера — только найти сами нормативные акты** (ссылку на публикацию/НПА, дату,
тип и т.п.) и отдать их на дальнейший разбор; извлечение содержания и заполнение карточки
меры делает уже эксперт/агент автообновления за пределами этого парсера.

**Формат документов:** HTML-страницы публикаций и PDF (многие НПА приложены как PDF) —
нужна поддержка обоих (см. раздел 3 — PyMuPDF/pdfplumber + pytesseract fallback).

**Определение новизны публикации:**
- Основной критерий — дата публикации на самом источнике (сравнение с датой последнего
  успешного обхода / с последней увиденной датой по этому источнику, per-источник).
- Дополнительно — смысловая валидация: с какой даты фактически вступает/действует
  изменение (дата в тексте акта может отличаться от даты публикации на портале) — эвристики
  на regex первой итерацией («вступает в силу с…»), LLM-разбор вторым проходом, если
  покрытие окажется низким по итогам пилота.
- Дедупликация: если публикация уже была обработана (по URL/ID документа) — новая карточка
  не создаётся.

**Ограничения по географии, типу документа, типу события, тематике, дате, типу контента**
— полностью соответствуют исходному ТЗ (`docs/Требования_к_мониторингу_изменений_в_НПА.html`,
раздел 5): федеральный/региональный уровень с определением региона по справочнику →
домену → тексту → «РФ»/«Не определён»; только публикации с привязкой к НПА конкретных
типов (федеральный закон, указ Президента, постановление Правительства, приказ
федерального министерства, региональные аналоги); только события «принятие/изменение/
отмена/вступление в силу/изменение параметров меры»; окно поиска — 24 часа при ежедневном
запуске, 7 дней при первом; только текстовые публикации.

**Доверстывание пропусков:** если обход в какой-то день не состоялся (сбой), при следующем
успешном запуске парсер обязан пройтись и по пропущенному периоду (не терять сигналы), а не
только «за последние 24 часа». Логика: хранить дату последнего успешного обхода per-источник
и от неё вести окно поиска, а не жёстко «today only».

## 5. Фильтрация по ключевым словам

**5.1 По ЖС:**
- Ветераны боевых действий: «ветеран боевых действий», «ВБД», «ветеран СВО».
- Люди с инвалидностью: «инвалид», «ребёнок-инвалид», «лицо с ограниченными
  возможностями», «инвалид с детства», «инвалид по зрению».
- Участники СВО: «участник СВО», «мобилизованный», «контрактник», «доброволец», «члены
  семей участников СВО», «дети участников СВО».

**5.2 Тематический блок мер поддержки:** «мера поддержки», «выплата», «льгота»,
«пособие», «компенсация», «субсидия».

**5.3 Маркеры документа:** «постановление», «указ», «закон», «приказ», «распоряжение».

**5.4 Маркеры сути:** «принят», «утверждён», «подписан», «вступил в силу», «внесены
изменения».

Публикация релевантна, если одновременно: содержит ключевые слова одной из ЖС **и**
слова из тематического блока мер поддержки.

**Классификация (уточнено относительно более ранней версии этого файла):** для MVP —
детерминированный первый проход по правилам 5.1–5.4 (`classifier.py`: ключевые слова →
категория/приоритет), без LLM в основном контуре классификации. LLM (провайдер **GLM**;
пример использования и креды пользователь предоставит отдельно) закладывается как
опциональный второй проход для узких мест с низким покрытием regex-правил — в первую
очередь для определения даты вступления в силу (раздел 4) и, при необходимости по итогам
пилота, для приоритета/реквизитов. Реализовывать через интерфейс/адаптер, не жёстко
встраивать вызов LLM в обязательный путь обработки каждой публикации.

## 6. Статусная модель сигнала

Статусы: **Новый → В работе → Отложен / Отклонён / Передан агенту → Завершён.**

| Статус | Кто присваивает | Когда | Действия эксперта |
|---|---|---|---|
| Новый | Парсер | сигнал создан, эксперт ещё не отреагировал | ✅ Взять в работу / ❌ Отклонить / ↩️ Позже |
| В работе | Эксперт | нажал «Взять в работу» | изучает сигнал, должен прислать ссылку на НПА |
| Отложен | Эксперт | ↩️ «Позже» | возвращается в очередь `/pending` и в следующую сводку |
| Отклонён | Эксперт | ❌ «Отклонить» + причина | обязательна причина из списка (см. ниже) или «Другое»; конечный статус |
| Передан агенту | Бот (автоматически) | после успешной проверки ссылки на НПА | ссылка уходит агенту автообновления, привязывается к `measureId` |
| Завершён | Эксперт | после проверки результата агента | сигнал уходит в `/history`, дальнейших действий не требует; конечный статус |

**Причины отклонения:** «Не относится к целевым категориям», «Дубликат», «Не является
НПА», «Другое».

**Переходы:**

| Из | В | Действие | Кто выполняет |
|---|---|---|---|
| Новый | В работе | ✅ Взять в работу | Эксперт |
| Новый | Отклонён | ❌ Отклонить + причина | Эксперт |
| Новый | Отложен | ↩️ Позже | Эксперт |
| В работе | Передан агенту | Отправка корректной ссылки на НПА | Бот автоматически |
| В работе | Отклонён | ❌ Отклонить | Эксперт |
| Отложен | В работе | ✅ Взять в работу | Эксперт |
| Отложен | Отклонён | ❌ Отклонить | Эксперт |
| Передан агенту | Завершён | Эксперт проверил результат агента | Эксперт |

## 7. Карточка сигнала — поля

- ID
- Категория (одна или несколько ЖС: ВБД / Инвалиды / СВО)
- Тип события: новый документ / изменение / отмена / вступление в силу / обзор
- Приоритет: высокий / средний / низкий
- Название документа (если извлечено)
- Реквизиты (если извлечены)
- Регион действия: «РФ» / конкретный субъект РФ / «Не определён»
- Ссылка на публикацию
- Дата и время создания
- Статус (раздел 6)

**Приоритизация:**
- Высокий — прямое указание на ЖС + слова «новый / изменение / отмена / утратил силу /
  индексация / повышение» + есть ссылка на документ.
- Средний — косвенная связь с ЖС, нет ссылки на полный текст, или регион не определён.
- Низкий — аналитика, обзор, интервью без указания на конкретный документ.

## 8. Словарь данных карточки меры (общий с методикой оценки, справочно)

Единая схема полей карточки меры (см. `docs/Для проверки обновления.xlsx`), используется
как справочник для привязки сигнала к конкретной мере (не создаётся/не заполняется этим
контуром, только читается/связывается):

- **Общие:** `measureId`, `region`, `measureName`, `measureSum` / `measure_first_group` …
  `measure_disabled_child`, `measurePeriodicity`, `measureTerms`, `department`,
  `measureType`, `measureLevel`, «Ссылка на источник», «Ссылка на НПА» (может быть
  несколько, с пунктом НПА), «Признак индексации».
- **Инвалиды:** `cause_general_disease`, `cause_war_trauma`, `cause_radiation`,
  `cause_disabled_child` (флаги 0/1) + суммы по группам инвалидности.
- **ВБД:** `СategoryOfVeteran`, `ListOfDocuments`, `HowToApply`, `Link`, `Contacts`,
  «Категория льготы».
- **СВО:** `categoryMobilized`, `categoryContractor`, `categoryVolunteer`,
  `kidsOfMilitary` (флаги 0/1).

`measureId` кодирует уровень: префикс `00_` = федеральная мера, `77_` = региональная
(Москва в примерах). Сравнение версий по годам (2025 vs 2026 для одного и того же
`measureId`) в исходном xlsx — способ увидеть, что именно меняет НПА (сумма выплаты,
условия, появление новых полей вроде «Признак индексации» или «Категория льготы»); формат
со временем расширяется новыми полями, поэтому справочник/схема должны допускать рост
полей без миграции кода приложения.

## 9. Команды бота

- `/today` — сигналы «Новый», «Отложен» за сегодня.
- `/pending` — все сигналы «В работе», «Отложен».
- `/history` — «Передан агенту» / «Завершён» / «Отклонён», последние 10.
- `/stats` — агрегированная статистика за неделю (по умолчанию).

## 10. Работа бота — сценарии

**Утренняя сводка** — пример:
```
Утренняя сводка — 18.08.2026
Найдено сигналов: 5
Высокий приоритет: 2 | Средний приоритет: 2 | Низкий приоритет: 1

1. Москва | Указ Мэра о новой выплате участникам СВО
   Источник: mos.ru
   /signal_1
...
```
Если новых сигналов нет — бот отправляет «Новых сигналов нет».

**Карточка сигнала** — категория, регион, тип события, приоритет, название, реквизиты,
источник, ссылка на публикацию, действия (✅/❌/↩️).

**Действия с сигналом:**
- ✅ Взять в работу → статус «В работе», бот запрашивает ссылку на полный текст НПА
  (поддерживаются HTML-страницы).
- ❌ Отклонить → бот запрашивает причину из 4 вариантов (раздел 6). Статус «Отклонён»,
  сигнал больше не показывается.
- ↩️ Позже → сигнал остаётся, бот напомнит в следующей сводке.

**Приём ссылки на НПА:** бот проверяет доступность страницы. Если недоступна — просит
проверить/прислать снова или загрузить файл напрямую. Если корректно — «✅ Ссылка
принята», статус → «Передан агенту», ссылка и привязанный `measureId` уходят агенту
автообновления.

## 11. Happy Path (сквозной сценарий)

1. 06:00 — парсер обходит источники.
2. ~08:00 (через ~2 часа после парсинга) — бот присылает эксперту сводку.
3. Эксперт открывает сигнал → ✅ «Взять в работу».
4. Бот просит ссылку на НПА (если не извлечена автоматически).
5. Эксперт отправляет/подтверждает ссылку.
6. Бот передаёт ссылку и привязанный `measureId` агенту автообновления.
7. Агент обрабатывает НПА, возвращает результат.
8. Эксперт проверяет результат → сигнал переходит в «Завершён» → уходит в `/history`.

---

## 12. Граничные случаи

**Парсинг:**
- Источник недоступен → 3 попытки, затем пропуск до следующего цикла (с сохранением
  «недообработанного» периода для доверстывания, раздел 4).
- Новых публикаций нет → бот отправляет «Новых сигналов нет».
- Публикация уже обработана → дубликат не создаётся (по URL/ID документа).

**Ссылка на НПА:**
- Ссылка недоступна → бот просит проверить и отправить ещё раз, либо загрузить файл
  напрямую.
- Если всё корректно → ✅ «Ссылка принята», статус → «Передан агенту».

**Эксперт / бот:**
- Сигнал более 3 дней в статусе «В работе» → бот присылает напоминание.
- Эксперт отклонил сигнал → сигнал помечается и не возвращается автоматически. Ручное
  повторное открытие — команда `/reopen <id>`, перевод в «Новый» с записью в историю
  статусов (не запрещено требованиями — там речь про автоматический невозврат).
- Эксперт нажал «Позже» → сигнал появится в следующей сводке.

## 13. Безопасность

- Бот работает только с whitelisted Telegram ID эксперта(ов). Сообщения от посторонних
  игнорируются.
- Все действия логируются.
- Передаваемые/принимаемые ссылки проверяются на допустимые домены (белый список раздела
  4) перед дальнейшей обработкой или передачей агенту.

## 14. Расписание

- **06:00** — ежедневный обход источников парсером (в исходном ТЗ есть расхождение
  06:00 vs 09:00 между разделом про happy path и разделом «Критерии готовности» — с
  заказчиком зафиксировано решение: **06:00**).
- **~08:00** — бот присылает эксперту сводку по найденным сигналам.
- Доверстывание пропусков — см. раздел 4.
- Напоминание о сигналах >3 дней в статусе «В работе» — ежедневная фоновая задача.

## 15. Критерии готовности

Система готова, если:
- парсер ежедневно (06:00) обходит федеральные, региональные и «иные» источники по
  белому списку доменов;
- бот присылает сводку (~08:00);
- эксперт может взять сигнал в работу, отклонить или отложить;
- бот принимает и проверяет ссылку на НПА;
- бот передаёт ссылку и `measureId` агенту автообновления (через адаптер, даже если
  контракт агента пока не подключён);
- добавление новой ЖС и нового региона выполняется через справочник без изменения кода;
- работают команды `/today`, `/pending`, `/history`, `/stats`;
- обрабатываются все описанные граничные случаи.

    услуг»). Исправлено: `parser/ru_stem.py` — допуск на словоформы через обрезку
    типичных окончаний (эвристика по длине слова, не морфология) с сохранением

    живой повторной проверкой): «доброволец» (ЖС «участник СВО») обрезался до
    «добровол», что матчилось на «добровольно»/«добровольный» — частые слова в не
    относящемся к СВО контексте («добровольное страхование» и т.п.). Причина —
    беглая гласная в русском склонении («доброволец» → «добровольца» теряет «е»
    перед «ц», и на этом же месте у «доброво́льный» стоит «ь» — падежные формы
    существительного неразличимы префиксным обрезанием от прилагательного ни при
    какой длине стема). Решение — `_EXACT_WORD_OVERRIDES` в `parser/ru_stem.py`:
    точечные исключения, сопоставляются целым словом без обрезки.

    ветке независимо написан второй `classifier.py` с эвристикой `_kw_hit` — обрезает
    последние 2 символа каждого слова ключевой фразы и ищет получившиеся «стемы» по
    отдельности, в любом порядке, в любом месте текста (в отличие от принятого решения
    выше, не требует смежности слов). Увеличивает recall, но ослабляет точность —
    ровно тот же класс риска, что и найденная коллизия «доброволец»/«добровольный»,
    только без защиты смежностью слов. Код не принят как есть при слиянии (см.
    `git log` — коммиты `2e75f5f`/`8c47582` в истории), но сохранён в истории git.

    Остаточные ограничения (не устранены, зафиксированы для полноты): некоторые
    прилагательные с чередованием в начале слова («новый»/«новая») по-прежнему не
    матчятся друг на друга; списки ключевых слов (особенно `topic_block`) всё ещё не
    исчерпывающие — расширять по мере обнаружения новых пропусков.
