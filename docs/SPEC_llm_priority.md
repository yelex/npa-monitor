# SPEC: LLM-приоритизация как второй этап после keywords-анализа

## Статус
Agreed (дизайн согласован с Claude 2026-08-24).

## Контекст
Приоритет сигнала сейчас — regex-эвристика `parser/classifier.py::detect_priority`:
HIGH = маркер документа + priority_high_word одновременно, MEDIUM = одно из двух,
LOW = ничего. LLM-слой уже есть (`parser/llm.py`, GLMClient; используется для
content-дедупа в `parser/dedup.py`). Прецедента батчинга в проекте нет.

Известная проблема пилота (Фаза 9 п.5) — недооценка (LOW вместо релевантного),
не переоценка HIGH.

## Проблема
Regex не видит сути события: «изменение размера выплаты с 10 000 до 15 000 ₽» и
«информационная статья о мерах поддержки» могут получить одинаковый приоритет.

## Решения (по итогам обсуждения с Claude, 2026-08-24)
1. **Скоуп:** LLM-проход только для сигналов с regex-приоритетом MEDIUM/LOW.
   HIGH не пересматривается — двойной гейт уже надёжен, LLM добавит шум.
2. **Батч:** 15–25 сигналов на вызов. Вход на элемент: `id`, `title`, `summary`
   (из `Publication`, до создания сигнала — summary в `Signal` не сохраняется),
   regex-trace (категории, event_type, region, matched priority-words).
   Ответ — строгий JSON `[{"id": int, "priority": "high|medium|low", "reason": str}]`,
   построчная валидация: битый/отсутствующий элемент → fallback на regex-приоритет
   этого сигнала. Один ретрай батча, дальше полный откат на regex.
3. **Критерии ранжирования (текст в промпте, «бизнес-аналитик»):**
   - Суть события (главный вес): новая мера > изменение суммы/условий выплаты >
     изменение порядка получения (без суммы) > информационная публикация без акта
   - Денежная составляющая: конкретная цифра/процент → выше
   - Срок вступления в силу: действует/ближайшее время → выше; отдалённая/неясная → ниже
   - Уровень власти — только уточняющий (регион уже отдельное поле карточки)
   Выход — сразу high/medium/low (enum `Priority`), без числовой шкалы.
4. **Комбинирование:** LLM сдвигает максимум на один уровень в любую сторону
   (`low↔medium`, `medium↔high`), не заменяет regex. Скачок low→high не применяется —
   логируется как расхождение для ручного разбора (сигнал о пробеле словаря или
   промпта). Любой сбой/невалидный ответ → regex-результат побеждает.
   Источник финального приоритета (`regex` vs `llm_adjusted`) — в структурированном
   логе (как `ClassificationTrace.format()`), поле в БД — при следующей миграции.
5. **Интеграция:** новый модуль `parser/llm_priority.py` (образец — `parser/dedup.py`):
   `refine_priorities_batch(session, signal_ids, llm_client)`. Вызов из
   `orchestrator.run_all` ПОСЛЕ основного цикла по источникам: собрать id сигналов
   прогона с MEDIUM/LOW (нужно небольшое расширение `SourceRunResult` — сейчас хранит
   только счётчики), чанки по 15–25, прогнать, закоммитить. `classifier.py` не
   трогаем; `llm_client=_UNSET` → `get_default_client()` — тесты с `llm_client=None`
   не затронуты.
6. **Аудит:** сначала неделя в режиме «только лог, не применять» (паттерн
   `scripts/cleanup_signals.py`: отчёт по умолчанию, `--apply` флагом). Сверка:
   `REJECTED` (not_target_category/duplicate) — regex не хуже LLM на LOW;
   `SENT_TO_AGENT`/`COMPLETED` — HIGH/MEDIUM ведут туда чаще; `status_history`
   (`NEW → IN_PROGRESS`) — гипотеза «эксперт быстрее берёт высокие приоритеты»:
   если LLM-приоритет коррелирует лучше regex — аргумент включать `--apply`.
   Скрипт `scripts/audit_priority.py` по образцу `audit_rejected_signals.py`.

## Как воспроизвести (текущее поведение)
1. Прогон парсера: сигнал с заголовком «Размер выплаты увеличен до 15 000 рублей»
   без маркера документа получает MEDIUM (или LOW), хотя событие high-value.
2. LLM-проход отсутствует — приоритет равен regex-результату всегда.
