# Спека: канонизация URL перед записью в `documents_seen`

Статус: **реализовано, 2026-08-24** (PLAN.md Фаза 9, п.2, первый под-пункт).

## 1. Проблема

Обратная связь аналитика (`signals_dump.txt`, AGENTS.md раздел 16 п.15, PLAN.md Фаза 9
п.2) — одна и та же публикация создаёт несколько сигналов, потому что
`db.service.register_document_seen` дедуплицирует по точному строковому совпадению
`doc_url` (`documents_seen.doc_url`, уникальный констрейнт), а один и тот же документ на
практике публикуется под разными, но эквивалентными по сути URL.

Примеры из дампа:

1. `http://publication.pravo.gov.ru/document/3401202608200009`,
   `...?index=9`, `...?index=10` — один и тот же приказ №1953 (сигналы [54]/[53]/[15]),
   `index` — служебный параметр листалки/вкладки на сайте pravo.gov.ru, не идентификатор
   документа.
2. `https://rg.ru/2026/08/21/.../v-voronezhskoj-oblasti-....html` vs
   `https://www.rg.ru/2026/08/21/.../v-voronezhskoj-oblasti-....html` — та же публикация
   RSS `rg.ru`, разница только в `www.` (сигналы [66]/[69]).

Отдельно замечен третий случай, который эта задача **не** закрывает (см. раздел 4):
`https://minjust.consultant.ru/documents/60711?items=1` vs
`https://minjust.consultant.ru/special/documents/document/60711?items=1` (сигналы
[49]/[24]) — тот же документ (`60711`), но разные пути на одном домене, не только разница
в query-параметрах или `www.`/схеме. Простая канонизация URL это не схлопнёт.

Синдикация по поддоменам `*.mos.ru` ([100]/[86]/[61]/[56]/[40] — район.mos.ru,
`www.mos.ru`, разные числовые ID в пути) — тоже вне периметра этой задачи: разные
домены и разные ID документа, не вариант одного URL. Это предмет второго под-пункта
Фазы 9 п.2 (дедуп по нормализованному заголовку/LLM-сравнение), не первого.

## 2. Решение

Новый модуль `parser/dedup.py::canonicalize_url(url: str) -> str`:

- схема: `http` → `https` (не различаем как разные документы из-за протокола);
- домен: нижний регистр, отбрасывается префикс `www.`;
- query-параметры: удаляются известные «шумовые» (список `NOISY_QUERY_PARAMS`,
  расширяемый, по аналогии с `parser/filters.py::_EXCLUDED_URL_PATTERNS`), оставшиеся —
  сортируются по ключу для стабильного порядка;
- fragment (`#...`) отбрасывается — не участвует в идентификации документа на
  практике встреченных источников;
- путь: убирается завершающий `/` (кроме корня `/`), не более.

`NOISY_QUERY_PARAMS` для MVP: `index` (pravo.gov.ru), `word_file`/`pdf_file` (варианты
формата документа на pravo.gov.ru — тот же документ, встречались в живой вёрстке при
разработке Фазы 3 адаптера `sources/pravo_gov.py`), `items` (minjust.consultant.ru —
чинит query-часть кейса 3, даже если не чинит путь целиком).

Точка подключения — `parser/orchestrator.py::_process_publication`: `register_document_seen`
вызывается с `doc_url=canonicalize_url(pub.url)`, а не с сырым `pub.url`. `Signal.source_url`
(что видит эксперт в карточке — AGENTS.md раздел 7) по-прежнему заполняется оригинальным
`pub.url` в `parser/signals.py::build_signal` — эксперту показываем реальную ссылку
источника, канонизация нужна только для внутреннего сравнения дублей.

`db.service.register_document_seen`/`db.models.DocumentSeen` не меняются — они уже
принимают `doc_url` как непрозрачную строку; канонизация — забота вызывающего кода
(`parser/`), не БД-слоя, по аналогии с тем, как `is_domain_whitelisted`/`is_excluded_path`
уже не в `db/`.

## 3. Что не делает эта задача

- Не трогает уже накопленные строки `documents_seen` за прошлые прогоны — старые
  нековичные URL там как есть (пере-дедуп задним числом не требуется: цель — не
  создавать новые дубликаты вперёд, не схлопнуть уже созданные сигналы).
- Не решает случай 3 (consultant.ru, разные пути на одном документе) и синдикацию
  `*.mos.ru` целиком — оба требуют второго слоя дедупа (нормализация заголовка/дата
  события, при необходимости LLM-сравнение через `parser/llm.py`, решение пользователя
  от 2026-08-24, AGENTS.md раздел 5) — отдельная задача, следующий под-пункт Фазы 9 п.2.
- Не меняет статус «Отклонён» на исходном сигнале и не защищает от повторного создания
  сигнала на тот же канонический URL после отклонения экспертом — это отдельный
  под-пункт (Фазы 9, п.3), зависит от этой задачи (использует тот же `canonicalize_url`),
  но не реализуется здесь.
