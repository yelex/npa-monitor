# Спека: применение результатов агента к базе мер (write-back) + пометка ручных правок

Статус: **черновик v2 (2026-08-27)** — переписана после решения Алексея: цель не
правка текста отчёта, а селективное применение диффа коннектора к базе мер.
Связанные: SPEC_autoupdate_agent_contract.md, npa-somas `docs/specs/
npa-monitor-spool-connector.md` (v3, «запись в базу НЕ входит» — эта спека её
добавляет как следующий шаг), SPEC_e2e_change_measure_id.md.

## 1. Контекст

Коннектор npa-somas (`revision/spool_connector/`) уже считает по задаче change
полевой дифф «было → стало» между KB-записью и экстракцией из акта, но упаковывает
его в `details` (markdown) — аналитик читает и делает `/complete`, данные никуда
не идут. Дифф машинный (`FieldDiff`: label, was, now, status exact/partial/no/na/range),
но наружу отдаётся только текстом.

## 2. Проблема

Аналитик проверил результат и хочет **принять дифф выборочно, по отдельным полям**
(изменить поле меры / не принять / удалить значение), с фиксацией того, что запись
была обновлена вручную. Сейчас применить результат к KB невозможно.

## 3. Решение

### 3.1 Расширение контракта результата (v3, schema_version 3)

В `results/<task_id>.json` рядом с текстовым `details` добавляется машиночитаемое
поле:

```json
"changes": [
  {"field": "measure_sum", "was": "195 000 ₽", "now": "200 000 ₽",
   "match": "exact" | "partial" | "no" | "na" | "range"},
  ...
]
```

- `field` — имя поля KB-записи (имена экстрактора и KB совпадают 1:1, см. спеку
  коннектора). Для `new`-задач (кандидаты без меры) — `changes` отсутствует,
  write-back не применим (MVP).
- `details` остаётся как есть (читабельный отчёт). Двойной источник — осознанно:
  `details` для человека, `changes` для машины; расхождения невозможны, т.к.
  генерируются одним кодом.
- Старые результаты (schema_version 2, без `changes`) бот просто показывает как
  раньше.

### 3.2 Помощь коннектору: боту нужны имена полей, не только текст

`bot/main.py::result_card` рендерит `changes` списком с чекбоксами (inline-кнопки:
✅ принять / ⏭ пропустить / ✏ ввести своё значение reply'ом). Это переворачивает
решение «команды vs кнопки» из v1 спеки: без кнопок выбор полей невыносим.

### 3.3 Хранение: overlay-таблица в БД npa-monitor, НЕ правка KB-файла

KB (`benefits_knowledge_base.json`) — **перезаливаемый снапшот** (решение Алексея,
спека коннектора). Писать ручные правки прямо в него нельзя: следующая перезаливка
их сотрёт. Поэтому:

- Новая таблица `measure_overrides` (SQLite, npa-monitor):
  - `id` PK, `measure_id`, `field`, `old_value` JSON, `new_value` JSON
    (new = null → «удалено аналитиком»),
  - `signal_id` FK, `source` = "agent_diff" | "manual",
  - `changed_by` (uid), `changed_at` UTC, `task_id`.
- Один override = одна правка одного поля; повторная правка того же поля той же
  меры — новая строка (история), «актуальность» = последняя по `changed_at`.
  **Дедуп по `(measure_id, field, task_id)`** (ревью-2026-08-27 №4): один и тот же
  результат не применяется к одному полю дважды (даблтап/ретрай игнорируется);
  после успешного «Применить» клавиатура карточки убирается
  (`edit_message_reply_markup`).
  Колонка `base_row_hash` — row_hash KB-записи, против которой считался дифф
  (для детекта STALE, см. ниже).
- **Индикатор «обновлено вручную»** — derivable: мера имеет хотя бы один override
  → карточки/саджест помечают её «✏️ правлено 27.08» (по последнему override).
  Отдельной колонки в KB не нужно.
- Потребители (саджест мер в боте, коннектор при diff): KB-снапшот + overlay =
  актуальное состояние. Коннектору — применение overlay при загрузке KB через
  экспорт (в npa-somas, см. ниже). **Детект STALE — на стороне npa-monitor**
  (у него есть и overlay, и row_hash из результата): если `base_row_hash`
  override не совпал с текущим row_hash KB-записи — override STALE, показать
  аналитику на пересмотр (коннектор ничего не помечает — у него нет записи в БД бота).
- **Whitelist полей KB** (ревью №7): при записи overlay имя поля валидируется
  против фиксированной схемы KB; неизвестное поле — отклонять и логировать,
  не сохранять (тихая порча формата при экспорте недопустима).
- **Проверка конфликта при применении** (ревью №9): перед записью сверять `was`
  из карточки с текущим эффективным значением поля (KB + overlay); при
  расхождении — не писать молча, показать аналитику «поле уже менялось после
  этого диффа, актуально X» и переспросить.
- **Атомарность батча** (ревью №10): все принятые поля одной карточки — один
  commit (частичное применение исключено).
- FK `signal_id`: `ondelete=SET NULL` — история правок переживает удаление сигнала
  (мера важнее сигнала).

### 3.4 Применение (write-back)

- **Парсенный payload (вкл. `changes[]`) сохраняется в БД до архивации файла**
  (ревью №3): таблица `signal_results` (task_id unique, payload JSON, received_at).
  Callback-кнопки адресуют запись по компактному `callback_data`
  `ovr:<task_id>:<field_idx>:<action>` (лимит 64 байта — исходные was/now туда
  не влезают). Промежуточный выбор (принял/пропустил) живёт в той же записи
  (JSON-поле `selection`) — переживает рестарт бота.
- Карточка результата: `details` как сейчас (через `_split_message`), а
  **`changes[]` + клавиатура — отдельным сообщением** (ревью №5): кнопки не
  привязаны к чанкам; при большом числе полей — постраничная клавиатура.
  Кнопки поля: ✅ принять / ⏭ пропустить / ✏ своё значение (reply) / 🗑 удалить
  (= `new_value: null`, ревью №6) + «Применить выбранное».
- Аналитик отмечает поля → «Применить» → **одна транзакция** на батч: строки в
  `measure_overrides` + обновление `selection` в `signal_results`. Сигнал
  остаётся в IN_PROGRESS до явного `/complete`.
- **Автоэкспорт после каждого «Применить»** (ревью №1 — блокер, не опция):
  иначе следующий прогон агента по той же мере посчитает дифф от до-overlay
  baseline и наврёт в match-метках. Экспорт синхронно после записи overrides.
- Экспорт актуального состояния KB: скрипт `scripts/export_kb.py` —
  снапшот + overlay → новый `benefits_knowledge_base.json` с пересчитанным
  `row_hash`. Заливка в оба места (бот + коннектор) одной операцией — инвариант
  сохраняется. **Кэш мер в боте** (`db/measures.py::_load_records`, lru_cache
  по пути, ревью №8): после экспорта обязателен сброс кэша/рестарт бота —
  зафиксировать в процедуре экспорта (MVP: рестарт).
- Удаление поля меры аналитиком: `new_value = null` — при экспорте поле
  записывается как null (не удаляется ключ — схема KB фиксированная).

## 4. Решения по открытым вопросам (после ревью 2026-08-27)

1. Экспорт — **авто после каждого «Применить»** (блокер, иначе дифф врёт).
2. «Применить» ≠ завершение: `/complete` остаётся отдельным шагом аналитика.
3. Флаг «правлено» в экспортируемом KB — вне MVP, решить при проектировании
   единого сервиса базы.

## 5. Как воспроизвести проблему

1. E2E как в SPEC_e2e_change_measure_id (sig-155): дифф приходит текстом.
2. Аналитик согласен с изменением суммы — применить некуда: ни KB, ни overlay,
   ни пометки «правлено вручную» не существует.
